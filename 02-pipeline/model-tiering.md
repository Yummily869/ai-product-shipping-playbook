# 模型分层调度

> 同一条链路里不同节点该用什么档位的模型，判断依据是什么。

---

## 结论先行

判断一个节点该用大模型还是小模型，看两个变量：

> **错误传播代价 × 调用频次**

| | 调用频次低 | 调用频次高 |
|---|---|---|
| **错误传播代价高** | **必须用最强模型**<br>（错了全链路崩，且省不了多少钱） | **最难的象限**<br>（既要准又要省，考虑大模型+小模型协同） |
| **错误传播代价低** | 用便宜模型 | **必须用便宜模型**<br>（这里是成本大头） |

**「错误传播代价」是这个框架的核心概念**，也是最容易被忽略的维度。

---

## 什么是错误传播代价

链路上的节点不是平等的。**越靠前的节点，出错的破坏力越大**，因为错误会沿着链路一路放大。

以一条内容生成链路举例：

```
素材理解 → 高光识别 → 故事编排 → 文案生成 → 风格包装 → 渲染
   ↑                        ↑
错误传播代价最高        错误传播代价低
（认错了内容，          （文案不好看，
 后面全是错的）          但成片仍可用）
```

**具体差异**：

| 节点 | 出错的后果 | 用户感知 | 可否补救 |
|---|---|---|---|
| 素材理解 / 高光识别 | 选错了片段，成片内容完全不对 | 「这根本不是我想要的」 | ❌ 只能重新生成 |
| 故事编排 | 叙事逻辑混乱 | 「看着怪怪的」 | ❌ 需重新生成 |
| 文案生成 | 文案平庸或不贴切 | 「文案一般，但视频还行」 | ✅ 用户可手动改 |
| 风格包装 | 字体/转场不够好看 | 基本不影响 | ✅ 用户可手动改 |

**关键判断**：

> **理解类节点（把现实世界转成结构化信息）出错，是不可补救的。**
> **生成类节点（把结构化信息转成内容）出错，用户往往可以自己修。**
>
> 所以理解类节点值得付高价用最强模型，生成类节点应该用最便宜的。

---

## 一个真实的分层方案

某内容生成链路的模型配置：

| 节点 | 模型档位 | 分层理由 |
|---|---|---|
| **高光识别** | 视觉大模型（72B）+ 小模型（7B）协同 | 理解类，错误不可补救；但调用频次极高，需要协同降本 |
| **剪辑思路规划** | 视觉大模型（72B） | 需要跨素材的全局推理，小模型无法胜任 |
| 片段排序 | 通用文本模型 | 输入已是结构化信息，任务简单 |
| 文案生成 | 通用文本模型 | 生成类，用户可改 |
| 封面生成 | 通用文本模型 | 生成类，影响面小 |
| 智能包装 | 通用文本模型 | 生成类，影响面小 |

### 大小模型协同的具体做法

高光识别是「错误代价高 + 调用频次高」的最难象限。解法是**拆分子任务，按难度分配模型**：

```
大模型（72B）：理解每个片段「讲了什么」  ← 语义理解，必须准
小模型（7B） ：判断片段「边界在哪」      ← 相对机械，可用小模型
```

在示例场景中，边界判断平均每 5 秒执行一次（60 秒视频约 11 次调用）。如果这 11 次全部走大模型，成本会显著上升；而用小模型承担，成本占比可以压到很低。

**这个拆法的通用性**：

> 一个「看起来必须用大模型」的任务，往往可以拆成「**判断类子任务**」和「**理解类子任务**」。判断类通常可以降档。

常见的可降档子任务：
- 边界/分段判断
- 二分类过滤（是否包含人脸、是否有人声、是否为无效画面）
- 候选集预筛（先用小模型筛掉 80%，大模型只处理剩下的）
- 格式校验与规整

## 常见的分层反模式

### ❌ 反模式一：全链路统一用同一个模型

「反正都要调模型，用同一个方便管理」——这是成本失控最常见的原因。

在示例场景中，如果 4 个文本节点也用视觉大模型，成本会上升数倍，而效果提升接近于零（因为这些节点的输入已经是结构化文本，不需要视觉能力）。

### ❌ 反模式二：按「节点重要性」直觉分配

「文案很重要，用户第一眼看文案，所以文案要用最好的模型」——这个推理是错的。

**重要 ≠ 错误代价高。** 文案重要，但文案不好用户可以改；素材理解不重要（用户根本感知不到这个节点），但认错了整个成片就废了。

**判断依据是「错误能否被补救」，不是「用户是否在意」。**

### ❌ 反模式三：没有降级路径

只配一个模型，模型侧限流或超时时链路直接失败。

正确做法是**每个关键节点都有降级路径**：

| 场景 | 降级策略 |
|---|---|
| 大模型超时 | 降级到小模型，标记结果置信度较低 |
| 大模型限流（429） | 切换备用模型或备用 Key |
| 连续失败 | 熔断，走无 AI 的兜底逻辑（如按时间顺序简单剪辑） |

**降级触发条件必须明确写进设计文档**，而不是等出问题再临时加。

## 并发能力：分层的隐藏约束

选模型时容易只看单价和效果，忽略**并发上限**。

以真实约束举例：某模型 **QPM 120、QPS 2**。

**推导业务并发**：

```
每分钟可服务用户数 = QPM ÷ 单次业务操作的调用次数
```

如果一次业务操作需要调用该模型 4 次，那么理论上一分钟只能服务 **30 个用户**。

**这个数字必须在放量决策前算出来**，否则会出现一种很难排查的现象：

> 灰度 5% 时一切正常，灰度到 30% 时开始大面积排队和超时——**不是代码问题，是撞了并发天花板。**

**分层在这里的额外价值**：把高频调用从大模型移到小模型，不只是省钱，同时也是**给大模型的并发额度留出余量**。

## 落地检查清单

方案设计阶段逐项确认：

- [ ] 每个节点标注了「理解类」还是「生成类」
- [ ] 每个节点标注了「错误是否可被用户补救」
- [ ] 每个节点标注了「调用次数由什么变量决定」（素材数？时长？固定 1 次？）
- [ ] 高频节点是否已尽可能降档
- [ ] 高代价节点是否有大小模型协同的拆分空间
- [ ] 每个关键节点是否定义了降级路径与触发条件
- [ ] 按 QPM/QPS 折算的业务并发上限是多少
- [ ] 最坏输入（P99）下的单次成本是多少
