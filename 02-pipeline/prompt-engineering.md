# Prompt 工程设计

> 一个标准且高可用的 Prompt 应包含五个要素。但真正决定成败的不是有没有这五块，而是**每一块里写了什么**。

---

## 五要素结构

| 要素 | 作用 | 一句话定义 |
|---|---|---|
| **Role** 角色定义 | 收窄语言风格与知识域 | 模型扮演谁 |
| **Task** 核心任务 | 明确要产出什么 | 模型要做什么 |
| **Context** 上下文与输入 | 提供判断依据 | 模型基于什么做 |
| **Rules** 规则与约束 | 划定不可逾越的底线 | 模型绝不能做什么 |
| **Format** 输出格式 | 保证下游可消费 | 模型怎么返回 |

**先说结论**：这五块中，**Rules 和 Format 决定线上稳定性，Role 和 Task 决定效果上限，Context 决定效果下限**。

大多数人花 80% 精力在 Role 和 Task 上，但线上 80% 的问题出在 Rules 和 Format。

---

## Role · 角色定义

### 作用不是"扮演"，而是"收窄"

Role 的真实作用是**限定模型在哪个语言域和知识域里工作**。

❌ 无效的 Role：
```
你是一个专业的助手。
```
（没有收窄任何东西，等于没写）

✅ 有效的 Role：
```
你是一个专业的快手电商售后客服。
```
（同时收窄了：语言风格=客服话术、平台=快手、领域=电商售后、立场=平台方）

### 写 Role 的三个要点

**1. 加上平台/场景限定词**

「电商客服」和「快手电商客服」的差别在于后者会带出平台特有的表达习惯。**平台名是一个高信息密度的限定词。**

**2. 用职业身份而不是能力描述**

| ❌ | ✅ |
|---|---|
| 你擅长写吸引人的短视频文案 | 你是一名短视频平台的资深内容运营 |
| 你能准确理解视频内容 | 你是一名专业的视频剪辑师 |

**原因**：职业身份携带了一整套隐含的判断标准和工作习惯，能力描述只是一句形容词。

**3. 在多节点链路里，每个节点的 Role 应该不同**

这一点容易被忽略。同一条链路的六个节点，如果 Role 全写「你是一个视频剪辑助手」，等于放弃了 Role 的作用。

正确做法：

| 节点 | Role |
|---|---|
| 高光识别 | 你是一名专业的视频素材筛选师，擅长从大量素材中识别出最有表现力的片段 |
| 剪辑思路 | 你是一名短视频导演，擅长把零散素材编排成有起承转合的故事线 |
| 文案生成 | 你是一名短视频平台的资深内容运营，擅长写出符合平台调性的文案 |
| 智能包装 | 你是一名视频包装设计师，擅长为内容选择匹配的视觉风格 |

> **不同的 Role 会激活不同的判断标准。** 「导演」会考虑叙事节奏，「运营」会考虑传播效果——这正是你在各节点想要的。

---

## Task · 核心任务

### 关键：Task 要写「产出物」而不是「动作」

| ❌ 写动作 | ✅ 写产出物 |
|---|---|
| 分析这些视频素材 | 从这些素材中选出 5 个最具表现力的片段，并说明每个片段的入选理由 |
| 生成文案 | 为每个入选片段生成一句不超过 15 字的字幕文案 |

**原因**：写动作时模型不知道什么算完成，写产出物时完成标准是自明的。

### 多任务必须拆开，不要塞进一个节点

一个常见错误是把多个目标塞进一个 Prompt：

```
❌ 请分析这些素材，选出高光片段，排好顺序，写好文案，
   并推荐合适的视觉风格和背景音乐。
```

**问题**：
- 任务之间会互相干扰，模型会在某些子任务上敷衍
- 无法定位是哪个子任务失败
- 无法针对单个子任务优化
- 无法为不同子任务选择不同档位的模型

**正确做法**：拆成独立节点，每节点一个明确产出物。这也是链路设计的基础，详见 [节点怎么拆](./node-decomposition.md)。

### 把「判断依据」写进 Task

如果任务包含主观判断，必须给出判断依据，否则模型会用自己的标准。

❌
```
选出最精彩的片段。
```

✅
```
选出最具表现力的片段。判断依据按优先级：
1. 画面中有明确的人物动作或事件发生（优于静态风景）
2. 画面清晰、无明显抖动和虚焦
3. 构图完整（主体未被裁切）
4. 有情绪表达（笑、惊讶、专注等）
```

> **「最精彩」是无法执行的指令，「按这四条依据排序」是可以执行的。**

## Context · 上下文与输入

### 最容易出事的一块：多来源信息的语义冲突

Context 通常来自多个上游：知识库检索结果、用户画像、历史对话、上游节点输出、用户显式选择。

**这里有一条极其重要的规则**：

> **多个来源的信息拼进同一个 Prompt 时，必须保证它们的语义空间不重叠。重叠即冲突，冲突时模型的选择是不可预测的。**

### 一个真实案例：风格标签冲突

**现象**：用户明确选了「诗意表达」风格，生成的文案却是吐槽风。

**排查过程**：Prompt 里同时包含两类信息——
- 用户显式选择的**风格标签**：「诗意表达」
- 上游自动生成的**内容标签**：「搞笑日常」「吐槽」

**根因**：部分内容标签本身**携带了风格语义**。两类标签一起进 Prompt，模型面对矛盾指令只能二选一，而它选哪个是随机的。

**解法**：把两类标签的语义空间彻底解耦。

| 标签类型 | 只能描述 | 严禁出现 |
|---|---|---|
| 内容标签 | 拍了什么（客体、场景、事件） | 任何描述「怎么讲」的词 |
| 风格标签 | 怎么讲（语气、调性、叙事方式） | — |

具体落地：在生成内容标签的那个节点，加入明确约束：

```
内容标签只描述画面中客观存在的事物、场景和事件。
禁止输出任何带有情绪倾向、语言风格、叙事调性的词汇
（如：搞笑、治愈、吐槽、燃、致命、绝了）。
```

### 第二个坑：上游结果的错误复用

**现象**：用户没有输入任何意图，系统却生成了一个完全不相关主题的视频。

**根因**：链路在「用户无输入」时，错误地复用了上一个节点的推荐结果作为意图输入。

**这引出一条通用规则**：

> **每一个塞进 Context 的字段，都必须明确回答：它在什么条件下不应该被使用？**

检查表：

| Context 字段 | 来源 | 什么条件下不应使用 |
|---|---|---|
| 用户输入意图 | 用户 | — |
| 上游推荐结果 | 节点 N-1 | **用户已有显式输入时不应使用** |
| 历史对话 | 会话 | 超过 X 轮或话题已切换时不应使用 |
| 用户画像 | 画像服务 | 画像置信度低时不应使用 |
| 知识库检索 | RAG | 检索相关度低于阈值时不应使用 |

**最后一列是最容易漏的**，而漏掉它的后果就是上面那两个线上问题。

### 第三个坑：Context 越多效果越好？不是

Context 塞得越多，会带来三个问题：

| 问题 | 说明 |
|---|---|
| **成本线性上升** | Token 直接算钱 |
| **注意力稀释** | 关键信息被埋在大量无关信息中 |
| **冲突概率上升** | 来源越多，语义重叠的概率越大 |

**判断原则**：每个字段都要能回答「**去掉它，效果会变差吗？**」。没做过这个消融测试的字段，通常是可以去掉的。

## Rules · 规则与约束

**这是决定线上稳定性的一块，也是最被低估的一块。**

### Rules 的四类

| 类型 | 作用 | 举例 |
|---|---|---|
| **事实底线** | 防止捏造 | 不要捏造退款政策，政策相关内容必须严格来自提供的知识库 |
| **范围边界** | 防止越界 | 不涉及订单以外的话题；不承诺任何知识库中未提及的赔付 |
| **形式约束** | 保证可用 | 回复不超过 100 字；不使用 emoji |
| **格式纪律** | 保证可解析 | 直接输出 JSON，不要添加任何解释性文字、不要用代码块包裹 |

### 反面清单比正面要求更有效

一个反直觉但很实用的经验：

> **模型对「不要做 X」的遵循度，往往高于对「要做 Y」的遵循度**——前提是 X 写得足够具体。

对比：

| ❌ 抽象正面要求 | ✅ 具体反面清单 |
|---|---|
| 文案要具体生动 | 禁止输出以下类型的词：<br>• 无信息量的形容词：美好、精彩、难忘、治愈<br>• 空泛的总结句：这就是生活、记录美好时光<br>• 平台黑话：绝了、爱了、yyds |

**为什么反面清单更有效**：抽象要求需要模型自己理解标准，而具体禁词是可以直接匹配的。

### 用「维度强制组合」解决输出粒度过粗

**典型问题**：要求提取用户标签，模型返回「女性」「年轻」——语法正确但毫无信息量。

**这不是模型能力问题，是约束缺失问题。** 解法是**强制维度组合**：

❌
```
提取用户的标签。
```

✅
```
每个标签必须由「人群属性 + 场景 + 需求」三个维度组合而成，
缺少任一维度视为无效。

✅ 正确示例：
  - 25-30岁职场女性 / 通勤路上 / 想要快速产出朋友圈内容
  - 亲子家庭用户 / 周末出游后 / 想给孩子做成长记录

❌ 错误示例：
  - 女性（缺场景与需求）
  - 想剪视频（缺人群与场景）
  - 年轻用户（三个维度都缺）
```

> **「粒度」是一个模糊概念，但「必须包含三个维度」是一个可判定的约束。** 把模糊要求翻译成可判定的结构，是 Prompt 工程最核心的动作。

### Few-shot 必须包含错误示例

只给正确示例，模型不知道边界在哪。**对错示例配对给出，效果显著优于只给正确示例。**

结构：

```
✅ 正确示例（附上为什么正确）
❌ 错误示例（附上为什么错误）
```

「为什么」这一句是关键——它让模型学到的是**判断标准**而不是**表面模式**。

### Rules 里必须显式禁止的三件事

这三条几乎适用于所有需要结构化输出的场景，是从线上问题倒推出来的：

```
1. 直接输出 JSON，不要添加任何前置说明或后置总结
2. 不要用 ```json 代码块包裹
3. 不要输出思考过程
```

**为什么要写第三条**：即使推理模型的思考模式已在参数层关闭，Prompt 层再写一遍是低成本的双保险。

## Format · 输出格式

### 格式约束在 Prompt 侧和解析侧都要做

这是本章最重要的一条工程认知：

| 侧面 | 作用 | 单独做的后果 |
|---|---|---|
| **Prompt 侧** | 降低问题**发生率** | 总有漏网的，且换模型版本就复发 |
| **解析侧** | 降低问题**影响面** | 掩盖了上游问题，解析层越来越复杂 |

> **只做一侧都是错的。** Prompt 侧管发生率，解析侧管影响面，两者解决的是不同问题。

解析侧的完整做法见 [容错解析的演进](../03-robustness/robust-parsing.md)。

### Format 的写法

**1. 给出结构定义 + 一个完整示例**

```
输出格式（严格遵守，不要添加任何额外字段）：
{
  "segments": [
    {
      "index": 0,
      "reason": "入选理由，不超过20字",
      "score": 0.0
    }
  ]
}
```

**2. 字段约束写在字段旁边，不要单独列**

❌ 把「reason 不超过 20 字」写在 Rules 里
✅ 直接写在字段的示例值里

**原因**：就近约束的遵循度明显更高。

**3. 明确空结果的表达方式**

这一条极容易漏，而漏掉它就会产生「模型返回自然语言解释」的问题：

```
如果没有任何片段满足条件，返回 {"segments": []}，
不要返回任何解释性文字。
```

> **不定义"没有结果"怎么表达，模型就会用自然语言解释为什么没有结果**——而这会直接导致下游解析失败。

**4. 避免嵌套过深**

嵌套超过 3 层时，格式错误率显著上升。宁可拆成两个节点，也不要让单节点输出一个深层嵌套结构。

## 一个完整示例

把五要素拼起来（以电商售后客服为例）：

```
# Role
你是一个专业的快手电商售后客服。

# Task
根据用户的问题和提供的订单信息，给出安抚回应和明确的
退换货操作指引。产出物是一段可以直接发送给用户的回复。

# Context
【订单信息】
{order_info}

【知识库检索结果】
{retrieved_policy}

【历史对话】
{chat_history}
（注：若历史对话超过 5 轮或话题已切换，仅参考最近 2 轮）

# Rules
底线约束：
1. 退换货政策、时效、赔付标准必须严格来自【知识库检索结果】，
   禁止捏造或推测
2. 若知识库中没有相关政策，回复"这个问题我需要为您转接专员核实"，
   禁止自行给出结论
3. 不承诺任何知识库未明确提及的补偿

形式约束：
4. 回复不超过 100 字
5. 结构固定为：先安抚（1句）→ 再说明（1-2句）→ 最后给出下一步动作（1句）
6. 不使用 emoji，不使用感叹号超过 1 个

禁止输出：
7. 禁止使用无实质内容的安抚话术：
   "非常抱歉给您带来不便""感谢您的理解与支持"
8. 直接输出 JSON，不要添加任何前置说明或后置总结
9. 不要用代码块包裹，不要输出思考过程

# Format
{
  "reply": "发送给用户的回复文本",
  "need_transfer": false,
  "policy_source": "引用的政策条目ID，无引用时为空字符串"
}

若无法处理该问题，返回 {"reply": "", "need_transfer": true, "policy_source": ""}
```

**注意这个示例里几个刻意的设计**：

| 设计 | 目的 |
|---|---|
| Context 里写了历史对话的使用条件 | 防止过期上下文干扰 |
| Rules 第 2 条给了"不知道时说什么" | 防止知识库缺失时捏造 |
| Rules 第 5 条固定了回复结构 | 保证输出稳定性，便于人工抽检 |
| Rules 第 7 条列了禁用话术 | 反面清单比"要有诚意"有效 |
| Format 里有 `need_transfer` 字段 | 让模型能表达"我处理不了"，而不是硬答 |
| 明确定义了无法处理时的返回 | 防止返回自然语言解释 |

## Prompt 迭代的工作方法

### 每次只改一个变量

Prompt 调优最容易犯的错误是一次改三处，效果变好但不知道是哪一处起了作用。

**记录格式**：

| 版本 | 改动内容（仅一处） | 测试集通过率 | 结论 |
|---|---|---|---|
| v1 | 基线 | 62% | — |
| v2 | 增加禁用词清单 | 78% | ✅ 保留 |
| v3 | 增加 Few-shot 错误示例 | 85% | ✅ 保留 |
| v4 | Role 从"助手"改为"资深运营" | 84% | ➖ 无显著影响，可回退 |

**这张表本身就是 Prompt 的版本管理**，也是交接时最有价值的文档。

### 固定一个不变的基准测试集

Prompt 改动的效果必须在**同一批样本**上对比，否则数字没有可比性。

基准测试集的要求：
- 分布与线上一致（见 [模型选型 · 测试集](./model-selection.md)）
- **只增不改**——每次线上 badcase 都补进去，但已有样本不删
- 规模不必大，30-50 个高质量样本足够看出趋势

### 区分「改 Prompt 能解决」和「改 Prompt 解决不了」

这是最重要的判断，能避免大量无效投入。

| 现象 | 是否该改 Prompt |
|---|---|
| 同一输入跑 5 次，有成功有失败 | ✅ 是约束问题，改 Prompt |
| 同一输入跑 5 次，5 次都失败 | ❌ 能力缺失，改 Prompt 无用 |
| 某一类输入（如竖屏）全部失败 | ❌ 输入分布问题，见 [第 03 章](../03-robustness/input-distribution-trap.md) |
| 输出格式偶发错乱 | ✅ Prompt 加格式纪律 + 解析侧加容错，两边都做 |
| 输出里混着思考过程 | ❌ 先查参数配置，不是 Prompt 问题 |

> **在改 Prompt 之前先做这个判断，能省下大量时间。** 很多团队在能力缺失的问题上反复调 Prompt，调了两周毫无进展。

## 检查清单

**Role**
- [ ] 包含平台/场景限定词，不是泛泛的"专业助手"
- [ ] 用职业身份而非能力描述
- [ ] 多节点链路中各节点 Role 不同

**Task**
- [ ] 写的是产出物，不是动作
- [ ] 单节点只有一个明确产出物
- [ ] 主观判断给出了明确的判断依据与优先级

**Context**
- [ ] 各来源信息的语义空间无重叠
- [ ] 每个字段都写明了「什么条件下不应使用」
- [ ] 每个字段都做过「去掉会变差吗」的检验

**Rules**
- [ ] 有反面清单（具体禁词/禁用句式），不只有正面要求
- [ ] 模糊要求已翻译成可判定的结构约束（如维度强制组合）
- [ ] Few-shot 包含错误示例且说明了为什么错
- [ ] 显式禁止：解释性文字 / 代码块包裹 / 思考过程

**Format**
- [ ] 给了结构定义 + 完整示例
- [ ] 字段约束就近写在字段旁
- [ ] 明确定义了「无结果」的表达方式
- [ ] 嵌套不超过 3 层
- [ ] 解析侧也做了容错（不只靠 Prompt）

**迭代**
- [ ] 有固定的基准测试集，只增不改
- [ ] 每次只改一个变量并记录效果
- [ ] 改之前判断过「这是不是 Prompt 能解决的问题」
