# AI Product Shipping Playbook

> 一份 AI 产品的**工作框架手册**——从需求论证、模型选型、Prompt 设计、评测体系，到上线后的鲁棒性与成本控制。
>
> 不讲 Prompt 技巧合集，不讲模型原理，只讲**真正做决策时需要回答的问题**，以及每个决策的代价。

---

## 为什么写这个

AI 产品经理这个岗位有一个尴尬处境：

可参考的方法论几乎都停留在两端——要么是「Prompt 十大技巧」这种操作层技巧，要么是「大模型将重塑一切」这种趋势层判断。**中间那一层最需要的东西是空的**：需求背景该怎么论证才立得住？模型选型的三个维度谁优先？主观效果怎么变成可判定的分数？

而真正做过一遍才知道，这一层里有大量**不写下来就一定会重复踩的坑**：需求背景写得可以套用到任何产品上、选型时先讨论成本导致选出效果不达标的方案、评测打了总分但定位不到问题环节、Demo 惊艳但上线后问题一个接一个。

这个仓库尝试把这一层系统化。每一节都遵循同一个结构：

```
问题 → 现象 → 根因 → 解法 → 代价
```

**「代价」这一栏是刻意保留的。** 因为绝大多数产品决策不是「有没有更好的方案」，而是「愿不愿意付这个代价」。只写解法不写代价的方法论，通常没在真实项目里用过。

手册按 AI 产品的**实际推进顺序**组织，前半部分是决策框架，后半部分是落地问题：

```
【决策阶段】                        【落地阶段】

```

## 五条贯穿全书的核心认知

### 1. 一段可以套用到任何产品的需求背景，等于没有需求背景

「随着 AI 技术快速发展，用户对高效工具的需求日益增长」——把「视频创作」换成「客服」「电商」「教育」，这句话依然通顺。

**需求背景不是一段描述，而是一条逐层收窄的论证链**：市场层论证「为什么是现在」（哪个阈值被跨过了，在此之前为什么不行）→ 公司层论证「为什么是我们」（新功能放在现有链路哪里、会不会和老功能打架）→ 用户层论证「具体是谁在什么场景下痛」（至少 2-3 个角色，而非一个抽象用户）→ 竞品层论证「差异化在哪」（推演竞品动机，找到他们主动放弃的地方）。

详见 [需求背景怎么写才立得住](./01-scenario/requirement-background.md)。

### 2. 选型的三个维度是约束关系，不是权重关系

很多选型文档做成加权打分表：效果 ×0.5 + 速度 ×0.3 + 成本 ×0.2。**这是错的。**

三者是**依次收窄的约束**：能力匹配度是硬门槛（达不到直接淘汰，再便宜也是浪费）→ 性能时延是硬门槛（但可以用产品形态化解）→ **成本永远是最后一个维度**，在满足前两者的候选中选最便宜的。

> **如果你在选型时最先讨论成本，通常说明能力门槛还没定义清楚。**

详见 [大模型选型策略](./02-pipeline/model-selection.md)。

### 3. Demo 与上线之间隔着「输入分布」

Demo 用的是你精心挑选的输入。线上面对的是真实用户的输入分布——包括竖屏视频、纯黑画面、30 秒以内的碎片素材、没有人声的片段。

**AI 产品绝大多数线上问题，根因都是「输入分布与测试分布不一致」。** 这条认知的实际用法见 [输入分布陷阱](./03-robustness/input-distribution-trap.md)。

### 4. 成本结构决定产品形态，而不是反过来

在多模态产品里，视觉理解节点通常吃掉 **90% 以上**的成本。这意味着：

- 在文案生成节点上优化 Prompt 长度，是**无效努力**
- 想降本，只有两条路：**降低视觉节点的调用频次**，或**等更便宜的视觉模型**
- 而「降低调用频次」会直接改变产品形态（比如按素材时长分档处理）

所以成本不是上线前才算的财务问题，**它在方案设计阶段就应该介入**。详见 [04 章](./04-cost/)。

### 5. 非确定性不是缺陷，是需要被产品化的属性

传统产品里，同样的输入必然得到同样的输出，「失败」是异常。AI 产品里，同样的输入可能得到不同输出，**「部分失败」是常态**。

这带来的不是「要不要容错」的问题，而是一系列产品决策：
- 失败时给用户重试，还是自动降级到弱能力版本？
- 生成 4 个候选让用户挑，还是生成 1 个但保证质量？
- 错误信息告诉用户「失败了」，还是告诉他「你的素材不符合要求」？

这些都不是技术问题。详见 [03 章](./03-robustness/) 与 [错误码设计](./03-robustness/error-code-design.md)。

## 关于内容来源

本手册的案例来自实际的 AI 产品落地经历，涉及**多模态内容生成、对话式 Agent、图像生成、企业知识问答**四类形态。

所有案例均已做脱敏处理：
- 不包含任何未公开的业务数据、用户数据与财务数据
- 成本相关章节使用**公开模型定价**重新构造等价示例，仅保留结构与比例关系
- 涉及具体产品的问题，仅描述**技术现象与归因方法**，不涉及产品实现细节

## 关于「代价」这一栏

如果你只想快速找到解法，可以跳过每节末尾的「代价」。但我建议不要跳过。

一个例子：为了解决推理模型输出污染下游的问题，最直接的解法是关闭思考模式。**代价是模型在复杂推理任务上的质量会下降。** 所以正确的做法不是「全局关闭」，而是「按节点区分——需要推理的节点保留，只做格式化输出的节点关闭」。

**不知道代价，就不知道边界在哪。** 这是我认为方法论和口号的区别。
