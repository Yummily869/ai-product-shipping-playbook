# Skill · Prompt 撰写

> 用在什么时候：给工作流节点写 Prompt，或者调优现有 Prompt 的时候。

---

## 我一开始的误解

实习之前我以为 Prompt 工程就是「怎么把话说得让模型听懂」，看了很多技巧类的文章。

实际做下来发现，**我 80% 的时间花在了 Rules 和 Format 上，不是 Role 和 Task 上**。

因为 Role 和 Task 写差一点，效果会差但还能用；Rules 和 Format 写差一点，**下游直接解析失败，整条链路挂掉**。

这是我现在对五要素的理解：

| 要素 | 我的理解 |
|---|---|
| **Role** 角色 | 决定效果上限 |
| **Task** 任务 | 决定效果上限 |
| **Context** 上下文 | 决定效果下限（最容易出诡异问题） |
| **Rules** 规则 | **决定线上稳不稳定** |
| **Format** 格式 | **决定线上稳不稳定** |

---

## Role · 角色

### 我踩的坑：写了但没起作用

我第一版给六个节点写的 Role 全是同一句：

```
你是一个专业的视频剪辑助手。
```

后来我发现这等于没写。因为 Role 的作用是**收窄**——限定模型在哪个语言域和知识域里工作。「专业的助手」什么都没收窄。

改成每个节点不一样之后，效果有明显变化：

| 节点 | Role |
|---|---|
| 高光识别 | 你是一名专业的视频素材筛选师，擅长从大量素材中识别最有表现力的片段 |
| 剪辑思路 | 你是一名短视频导演，擅长把零散素材编排成有起承转合的故事线 |
| 文案生成 | 你是一名短视频平台的资深内容运营，擅长写符合平台调性的文案 |
| 智能包装 | 你是一名视频包装设计师，擅长为内容选择匹配的视觉风格 |

我的理解是：**「导演」会考虑叙事节奏，「运营」会考虑传播效果**——这些判断标准是职业身份自带的，你不用一条条写出来。

### 两个小经验

**① 加平台/场景限定词**

「电商客服」和「快手电商客服」不一样，后者会带出平台特有的表达习惯。平台名是个信息密度很高的词。

**② 用职业身份，不用能力描述**

| 差 | 好 |
|---|---|
| 你擅长写吸引人的短视频文案 | 你是一名短视频平台的资深内容运营 |
| 你能准确理解视频内容 | 你是一名专业的视频剪辑师 |

职业身份自带一整套隐含标准，能力描述只是一句形容词。

## Task · 任务

### 坑一：写了动作，没写产出物

| 我一开始写的 | 改成 |
|---|---|
| 分析这些视频素材 | 从这些素材中选出 5 个最有表现力的片段，并说明每个的入选理由 |
| 生成文案 | 为每个入选片段生成一句不超过 15 字的字幕文案 |

区别在于：写动作时模型不知道什么算做完，写产出物时完成标准是自明的。

### 坑二：一个节点塞了太多任务

我最开始想省事，写成这样：

```
请分析这些素材，选出高光片段，排好顺序，写好文案，
并推荐合适的视觉风格和背景音乐。
```

问题很快就出来了：
- 模型在某些子任务上明显敷衍（通常是排在后面的）
- 出问题时不知道是哪个子任务失败
- 没法针对单个子任务优化
- 没法给不同子任务用不同档位的模型

后来拆成了六个独立节点。**拆完之后最大的好处是能定位问题**——效果差的时候知道该改哪个节点的 Prompt。

### 坑三：主观判断没给依据

```
❌ 选出最精彩的片段。
```

「最精彩」是没法执行的指令，模型会用自己的标准。改成：

```
✅ 选出最有表现力的片段。判断依据按优先级：
1. 画面中有明确的人物动作或事件发生（优于静态风景）
2. 画面清晰、无明显抖动和虚焦
3. 构图完整（主体未被裁切）
4. 有情绪表达（笑、惊讶、专注等）
```

## Context · 上下文

**这一块是我遇到最多诡异问题的地方。** 两个坑都让我排查了很久。

### 坑一：两个来源的信息互相打架

**现象**：用户明明选了「诗意表达」风格，生成的文案却是吐槽风。

我一开始以为是文案节点的 Prompt 没写清楚，改了好几版都没用。

后来把完整 Prompt 打出来看，才发现里面同时有两组信息：
- 用户选的**风格标签**：「诗意表达」
- 上游自动生成的**内容标签**：「搞笑日常」「吐槽」

**问题在于：有些内容标签本身带了风格语义。** 两组标签一起进 Prompt，模型面对互相矛盾的指令只能二选一，选哪个是随机的。

**解法**是把两类标签的语义空间分开：

| 标签类型 | 只能描述 | 严禁出现 |
|---|---|---|
| 内容标签 | 拍了什么（客体、场景、事件） | 任何描述「怎么讲」的词 |
| 风格标签 | 怎么讲（语气、调性） | — |

在生成内容标签的那个节点加了约束：

```
内容标签只描述画面中客观存在的事物、场景和事件。
禁止输出任何带情绪倾向、语言风格、叙事调性的词
（如：搞笑、治愈、吐槽、燃、绝了）。
```

**我从这件事学到的**：多个来源的信息拼进同一个 Prompt 时，得先确认它们的语义空间不重叠。重叠就会冲突，冲突时模型选哪个是不可预测的。

### 坑二：上游结果被错误复用

**现象**：用户什么都没输入，系统却生成了一个完全不相关主题的视频。

**原因**：链路在「用户没输入」的情况下，把上一个节点的推荐结果当成了用户意图。

这让我意识到一件事：**每个塞进 Context 的字段，都得回答「它在什么条件下不该被使用」**。

我后来会列这张表：

| 字段 | 来源 | 什么条件下不该用 |
|---|---|---|
| 用户输入意图 | 用户 | — |
| 上游推荐结果 | 节点 N-1 | **用户已有显式输入时不该用** |
| 历史对话 | 会话 | 超过 X 轮或话题已切换 |
| 用户画像 | 画像服务 | 画像置信度低时 |
| 知识库检索 | RAG | 相关度低于阈值时 |

**最后一列是我一开始完全没想到要写的**，漏掉它就出了上面那个 bug。

### 坑三：Context 不是越多越好

我一开始的想法是「多给点信息模型判断得更准」，结果发现三个问题：

- **成本线性上升**（Token 直接算钱）
- **注意力被稀释**（关键信息埋在一堆无关信息里）
- **冲突概率变高**（来源越多，语义重叠概率越大）

我现在的判断方式：每个字段都问一遍「**去掉它，效果会变差吗？**」没做过这个测试的字段，通常都能去掉。

## Rules · 规则

这块我花的时间最多，因为线上问题基本都出在这。

### 最有用的一招：反面清单比正面要求管用

这个是我试出来的，有点反直觉：

> **模型对「不要做 X」的遵循度，往往高于对「要做 Y」的遵循度**——前提是 X 写得够具体。

对比一下：

| 我一开始写的 | 改成 |
|---|---|
| 文案要具体生动 | 禁止输出以下词：<br>• 无信息量的形容词：美好、精彩、难忘、治愈<br>• 空泛的总结句：这就是生活、记录美好时光<br>• 平台黑话：绝了、爱了、yyds |

我猜原因是：抽象要求需要模型自己理解标准，而具体禁词是可以直接匹配的。

### 第二招：把模糊要求翻译成可判定的结构

**遇到的问题**：要模型提取用户标签，它返回「女性」「年轻」——语法没错但完全没信息量。

我一开始以为是模型能力不行。后来发现是我的约束太模糊了——我说「要具体」，但「具体」是什么模型不知道。

改成**强制维度组合**之后立刻好了：

```
每个标签必须由「人群属性 + 场景 + 需求」三个维度组合而成，
缺少任一维度视为无效。

✅ 正确示例：
  - 25-30岁职场女性 / 通勤路上 / 想快速产出朋友圈内容
  - 亲子家庭用户 / 周末出游后 / 想给孩子做成长记录

❌ 错误示例：
  - 女性（缺场景与需求）
  - 想剪视频（缺人群与场景）
```

**我总结的规律**：「粒度」「具体」「生动」这类词都是模糊的，得翻译成可判定的结构约束（比如「必须包含三个维度」）。这个动作我觉得是 Prompt 工程里最核心的一件事。

### 第三招：Few-shot 要给错误示例

只给正确示例，模型不知道边界在哪。我现在会成对给：

```
✅ 正确示例（+ 为什么正确）
❌ 错误示例（+ 为什么错误）
```

「为什么」这句挺重要的——不写的话模型学到的是表面模式，写了才是判断标准。

### 我现在每个结构化输出节点都会写的三条

这三条是从线上问题倒推出来的：

```
1. 直接输出 JSON，不要添加任何前置说明或后置总结
2. 不要用 ```json 代码块包裹
3. 不要输出思考过程
```

第三条即使在参数层已经关了思考模式，我也会再写一遍——多写一句成本很低。

## Format · 输出格式

### 最重要的一条认知：Prompt 侧和解析侧都要做

这是我实习期间最有价值的一个收获：

| | 作用 | 只做一侧的后果 |
|---|---|---|
| **Prompt 侧** | 降低问题**发生率** | 总有漏网的，换个模型版本就复发 |
| **解析侧** | 降低问题**影响面** | 掩盖了上游问题，解析层越来越复杂 |

**两侧解决的是不同问题，只做一侧都不行。** 解析侧怎么做见 [容错解析演进](../../notes/容错解析演进.md)。

### 具体写法

**① 给结构定义 + 一个完整示例**

```
输出格式（严格遵守，不要添加任何额外字段）：
{
  "segments": [
    {
      "index": 0,
      "reason": "入选理由，不超过20字",
      "score": 0.0
    }
  ]
}
```

**② 字段约束就近写，别单独列**

「reason 不超过 20 字」写在字段示例里，比写在 Rules 里遵循度高——这个我对比过。

**③ 一定要定义「没有结果」怎么表达**

这条我一开始漏了，直接踩坑：

```
如果没有任何片段满足条件，返回 {"segments": []}，
不要返回任何解释性文字。
```

**不定义的话，模型会用自然语言解释为什么没结果**——然后下游解析直接失败。

**④ 嵌套别超过 3 层**

我试过嵌套 4 层，格式错误率明显上升。宁可拆成两个节点。

## 完整示例

我按五要素写的一个例子（客服场景，非我做过的项目，是我用来练手的）：

```
# Role
你是一个专业的快手电商售后客服。

# Task
根据用户的问题和提供的订单信息，给出安抚回应和明确的退换货操作
指引。产出物是一段可以直接发送给用户的回复。

# Context
【订单信息】
{order_info}

【知识库检索结果】
{retrieved_policy}

【历史对话】
{chat_history}
（若历史对话超过 5 轮或话题已切换，仅参考最近 2 轮）

# Rules
底线：
1. 退换货政策、时效、赔付标准必须严格来自【知识库检索结果】，
   禁止捏造或推测
2. 若知识库中没有相关政策，回复"这个问题我需要为您转接专员核实"，
   禁止自行给结论
3. 不承诺任何知识库未明确提及的补偿

形式：
4. 回复不超过 100 字
5. 结构固定：先安抚（1句）→ 说明（1-2句）→ 下一步动作（1句）
6. 不用 emoji，感叹号不超过 1 个

禁止：
7. 禁止使用无实质内容的安抚话术：
   "非常抱歉给您带来不便""感谢您的理解与支持"
8. 直接输出 JSON，不要添加前置说明或后置总结
9. 不要用代码块包裹，不要输出思考过程

# Format
{
  "reply": "发送给用户的回复文本",
  "need_transfer": false,
  "policy_source": "引用的政策条目ID，无引用时为空字符串"
}

若无法处理，返回 {"reply": "", "need_transfer": true, "policy_source": ""}
```

几个刻意的设计：

| 设计 | 为什么 |
|---|---|
| Context 写了历史对话的使用条件 | 防过期上下文干扰（我踩过的坑二） |
| Rules 第 2 条给了"不知道时说什么" | 不给的话模型会自己编 |
| Rules 第 7 条列了禁用话术 | 反面清单比"要有诚意"有效 |
| Format 有 `need_transfer` 字段 | 让模型能表达"我处理不了"，而不是硬答 |
| 定义了无法处理时的返回 | 不定义就会返回自然语言 |

## 调优的工作方法

### 一次只改一处

我一开始一次改三个地方，效果变好了但不知道是哪处起的作用，下次遇到类似问题完全没法复用。

现在我会记这张表：

| 版本 | 改了什么（只一处） | 测试集通过率 | 结论 |
|---|---|---|---|
| v1 | 基线 | 62% | — |
| v2 | 加禁用词清单 | 78% | ✅ 留 |
| v3 | 加 Few-shot 错误示例 | 85% | ✅ 留 |
| v4 | Role 从"助手"改"资深运营" | 84% | 没明显影响，可回退 |

这张表本身也是 Prompt 的版本管理，交接的时候很有用。

### 最省时间的一个判断

这个是我吃过亏才学会的——**改 Prompt 之前先判断这是不是 Prompt 能解决的问题**：

| 现象 | 该改 Prompt 吗 |
|---|---|
| 同一输入跑 5 次，有成功有失败 | ✅ 是约束问题，改 Prompt |
| 同一输入跑 5 次，5 次全失败 | ❌ 能力缺失，改 Prompt 没用 |
| 某一类输入（比如竖屏）全部失败 | ❌ 输入分布问题，见 [竖屏双字幕](../../notes/竖屏双字幕.md) |
| 输出格式偶发错乱 | ✅ 两边都做（Prompt + 解析容错） |
| 输出里混着思考过程 | ❌ 先查参数配置，不是 Prompt 问题 |

**「同一输入跑 5 次」这个动作特别值。** 我有一次在一个能力缺失的问题上调了很久 Prompt，后来才发现跑几次都是同一个结果——那根本不是 Prompt 能解决的。

## 自检清单

**Role**
- [ ] 有平台/场景限定词，不是"专业助手"
- [ ] 用职业身份，不是能力描述
- [ ] 多节点链路里各节点 Role 不同

**Task**
- [ ] 写的是产出物，不是动作
- [ ] 一个节点只有一个产出物
- [ ] 主观判断给了明确依据和优先级

**Context**
- [ ] 各来源信息的语义空间不重叠
- [ ] 每个字段写明了「什么条件下不该用」
- [ ] 每个字段做过「去掉会变差吗」的测试

**Rules**
- [ ] 有具体的反面清单，不只有正面要求
- [ ] 模糊要求已翻译成可判定的结构约束
- [ ] Few-shot 有错误示例且说明了为什么错
- [ ] 显式禁止：解释性文字 / 代码块 / 思考过程

**Format**
- [ ] 有结构定义 + 完整示例
- [ ] 字段约束就近写在字段旁
- [ ] 定义了「无结果」怎么表达
- [ ] 嵌套不超过 3 层
- [ ] 解析侧也做了容错

**调优**
- [ ] 有固定测试集
- [ ] 一次只改一处并记录
- [ ] 改之前判断过这是不是 Prompt 能解决的

## 我还没搞清楚的

- 「反面清单比正面要求有效」我只在文案生成这类任务上验证过，不知道在别的任务类型上是不是也成立。
- Few-shot 给几个例子最合适？我一般给 2-3 对，但没测过给 5 对会不会更好。
- 测试集我只有 30 多个样本，不知道这个规模够不够看出真实趋势。
