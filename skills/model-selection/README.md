# Skill · 模型选型

> 用在什么时候：方案设计阶段决定每个节点用什么模型的时候。

---

## 我一开始做错的地方

第一次做选型，我列了这样一张表：

| 模型 | 效果 | 速度 | 成本 | 加权总分 |
|---|---|---|---|---|
| A | 9 | 6 | 5 | 7.0 |
| B | 7 | 8 | 8 | 7.6 |

按这张表 B 赢了。但实际上 B 的效果不达标——**效果不达标的模型再便宜也没用，用户不会用，Token 白花。**

后来我理解到：这三个维度不是可以互相补偿的权重，而是**依次收窄的约束**：

```
Step 1 · 能力匹配度  → 达不到直接淘汰（硬门槛，不能用便宜弥补）
   ↓ 剩下的候选里
Step 2 · 性能时延    → 超出用户耐受淘汰（但可以用产品形态化解）
   ↓ 剩下的候选里
Step 3 · 成本        → 在满足前两者的候选中选最便宜的
```

**成本永远是最后一个维度。** 我现在的判断是：如果选型时最先讨论成本，通常说明能力门槛还没定义清楚。

---

## 一 · 能力匹配度

### 「效果好」是没法验证的，得拆成子能力

我一开始写「这个模型视频理解能力强」，被研发问「强在哪」，答不上来。

后来学会拆成子能力 + 判定方法：

| 子能力 | 为什么需要 | 怎么判定 |
|---|---|---|
| 画面主体识别 | 决定能否知道「拍了什么」 | 抽 50 个片段人工核对 |
| 场景/环境判断 | 决定文案能否贴合环境 | 同上 |
| 动作与事件理解 | 决定能否识别高光时刻 | 标注 30 个含明显事件的片段看召回 |
| 时序理解 | 决定能否判断片段先后 | 打乱顺序看能否还原 |
| 情绪/氛围判断 | 决定风格包装是否合适 | 主观评分，双人交叉 |

拆到这个粒度才能做决策。因为不同模型的强项不一样——有的主体识别很强但时序理解很弱。**如果你的场景不依赖时序，那个模型就是合适的。**

### 我学到最有用的一招：同一输入跑 5 次

这个动作能区分两种完全不同的问题：

| 类型 | 表现 | 该怎么办 |
|---|---|---|
| **能力缺失** | 5 次全失败 | 换模型，或者在产品层规避（前置校验/功能不开放） |
| **能力不稳定** | 有成功有失败 | 加约束（Prompt / 后处理） |

我有一次把「不稳定」误判成「缺失」，差点建议换模型，白折腾了一段时间。跑 5 次这个动作花不了几分钟，但能省很多事。

### 最容易翻车的地方：测试集分布

这个是我吃过大亏的。

> **在标准样本上选出的模型，可能在真实输入上表现完全不同。**

我们爆款复刻的字幕消除能力，在横屏视频上表现良好，在竖屏上大面积失效。而竖屏是我们线上的主要分布——这个问题一直到提测才暴露，badcase 率 70%。详细过程见 [竖屏双字幕](../../notes/竖屏双字幕.md)。

**如果选型阶段的测试素材里竖屏占比够高，这个问题会在选型时就被发现。**

所以我现在做选型测试集会先填这张表：

| 维度 | 线上真实分布 | 我的测试集分布 | 对齐了吗 |
|---|---|---|---|
| 画幅比例 | 竖屏 90% | | |
| 时长分布 | P50 / P99 | | |
| 垂类分布 | 各垂类占比 | | |
| 极端输入 | 空/纯黑/无声/超短/超长 | | |

**任何一行没对齐，都是一个潜在的线上问题。** 这张表是我实习期间做的最有价值的一个模板。

## 二 · 性能与响应时延

### 三个要分开算的时间

| 指标 | 定义 | 影响什么 |
|---|---|---|
| 首 Token 延迟 | 请求到收到第一个字 | 流式场景的体感 |
| 单节点耗时 | 该节点完整执行时间 | 链路总耗时的构成 |
| **端到端耗时** | 用户点击到看到结果 | **用户实际感知的唯一指标** |

我一开始只看单节点耗时，觉得每个 3 秒挺快的。但六个节点串起来是 18 秒——**18 秒已经超出多数人在没有进度提示时的耐受了。**

### 一个我差点漏掉的约束：并发上限

选型时容易只看单价和效果，忘了看并发。

我们用的一个模型是 **QPM 120、QPS 2**。

```
每分钟能服务多少用户 = QPM ÷ 单次业务操作调用它的次数
```

如果一次操作要调 4 次，那一分钟只能服务 30 个用户。

**这个数字得在放量前算出来。** 否则会出现一种很难排查的情况：灰度 5% 一切正常，灰度到 30% 开始大面积排队超时——不是代码问题，是撞了并发天花板。

### 时延超标时，我觉得应该先想产品方案

这是我认为产品经理比研发更该主动提的判断。**很多时延问题不需要技术解决**：

| 产品手段 | 适用条件 |
|---|---|
| 异步化 + 消息通知 | 结果不需要立即消费 |
| 分阶段返回 | 链路可分段产出（先出文案，视频后台渲染） |
| 进度可视化 | 没法缩短耗时时，能明显提升耐受度 |
| 预生成 / 缓存 | 输入可预测 |
| 降级快路径 | 有低成本备选方案 |

**判断顺序我觉得应该是：能不能改产品形态 → 能不能优化链路 → 最后才考虑换更快但效果更差的模型。** 因为换快模型通常意味着效果下降，而效果是硬门槛。

### 一个真实的坑：以为模型慢，其实是参数没配对

有个节点单次调用要 **72 秒**，我一直以为是模型太慢。

后来排查出来是推理模型的思考模式默认开着。显式关掉之后降到 **2.5 秒**，Token 从 4500 降到 750。

> **在判断「这模型太慢」之前，先确认所有参数都是显式设置的。** 详细过程见 [思考过程污染](../../notes/思考过程污染.md)。

## 三 · 成本评估

前两个维度筛完了才看成本。

### 得按「一次业务操作」算，不能按「单次调用」算

我一开始的算法是错的：「这个模型 0.03 元一次调用，很便宜」。

问题是用户生成一条成片要调它 8 次，加上其他节点，实际总成本完全不是这个量级。

**正确的算法是挂在用户能感知的动作上**：「用户生成一条成片的成本是 X 元」。这个数字才能用来推定价。

中间的换算关系（一次成片 = 多少次调用）必须写清楚，因为它会随输入规模变化。

### 要算三档，不是一个数

| 场景 | 输入规模 | 用途 |
|---|---|---|
| 典型 | P50 输入 | 算单位经济模型、定价 |
| 较重 | P90 输入 | 评估日常波动 |
| **最坏** | P99 输入 | **决定要不要加产品硬限制** |

**我一开始只算了平均值。** 后来意识到：如果用户传了 20 个 5 分钟素材，成本可能是平均值的几十倍。平均成本可控不代表长尾可控。

### 我观察到的一条规律（但样本只有一个项目）

在我做的智能剪辑链路里，成本占比大概是这样：

| 节点 | 模型类型 | 占比 |
|---|---|---|
| 高光识别 | 视觉大模型 + 小模型 | **≈ 63%** |
| 剪辑思路 | 视觉大模型 | **≈ 31%** |
| 片段排序 | 文本模型 | ≈ 2.8% |
| 文案生成 | 文本模型 | ≈ 1.6% |
| 封面生成 | 文本模型 | ≈ 1.2% |
| 智能包装 | 文本模型 | ≈ 1.0% |

**两个视觉节点占了 94%，四个文本节点加起来不到 7%。**

（数值已按公开模型定价重新构造为等价示例，只保留比例关系。）

我理解的原因是三个因素叠加：
- **单价差约 10 倍**（视觉模型 vs 文本模型）
- **Token 量差几十倍**（一张图 700-800 Token，视频按帧采样，fps=1 分析 60 秒 = 约 45000 Token）
- **调用次数也更多**（逐片段分析、边界判断）

**这条规律对我的实际影响**：我意识到在文案节点精简 Prompt 是无效努力（该节点只占 1.6%，砍一半省 0.8%）。真正有效的只有降低视觉节点的调用频次，或者等更便宜的视觉模型。

⚠️ **需要说明**：这个比例是我在这一个项目里观察到的，换成别的产品结构可能完全不同。我没有别的样本可以验证。

### 我漏算过的成本项

| 漏项 | 说明 |
|---|---|
| **失败也要付钱** | 调用发出就消耗 Token，失败结果不产生价值 |
| 用户重新生成 | AI 产品里这个行为频率很高 |
| 前置辅助服务 | 转码、字幕擦除、ASR |
| 存储与 CDN | 生成物的存储分发 |

**第一行让我意识到一件事**：提升成功率本身就是降本手段，而且它不牺牲任何体验。一个 20% 失败率的链路等于凭空多付 20% 成本。

## 结论应该是分节点选型，不是选一个模型

三个维度走完，结论不该是「我们选 X 模型」，而是「每个节点各用什么档位」。

我用的判断依据是：**错误传播代价 × 调用频次**

| | 调用少 | 调用多 |
|---|---|---|
| **错误代价高** | 用最强模型 | 最难的象限：大模型+小模型协同 |
| **错误代价低** | 用便宜模型 | **必须用便宜的**（这里是成本大头） |

### 「错误传播代价」怎么判断

我的标准是：**这个错误用户能不能自己补救？**

| 节点 | 出错后果 | 能补救吗 |
|---|---|---|
| 素材理解 / 高光识别 | 选错片段，成片内容完全不对 | ❌ 只能重新生成 |
| 剪辑思路 | 叙事逻辑混乱 | ❌ 需重新生成 |
| 文案生成 | 文案平庸 | ✅ 用户可手动改 |
| 风格包装 | 字体转场不好看 | ✅ 用户可手动改 |

**所以理解类节点值得付高价，生成类节点应该用最便宜的。**

我觉得这里有个反直觉的点：文案是用户第一眼看到的，感觉最重要，但因为用户能自己改，所以不该给它最好的模型。**「重要」和「错误代价高」是两件事。**

### 大小模型协同

高光识别是「错误代价高 + 调用频次高」这个最难的象限。我们的做法是拆子任务：

```
大模型：理解每个片段「讲了什么」   ← 语义理解，必须准
小模型：判断片段「边界在哪」       ← 相对机械，小模型够用
```

边界判断平均每 5 秒执行一次，60 秒视频要判断 11 次。这 11 次全走大模型成本会明显上升。

**我从这里总结的一条**：一个「看起来必须用大模型」的任务，往往能拆成「判断类子任务」和「理解类子任务」，判断类通常可以降档。

---

## 选型结论要包含降级方案

我一开始的选型文档只写了「选什么」，没写「不可用时怎么办」，被研发问住了。

| 故障场景 | 降级策略 | 触发条件 |
|---|---|---|
| 超时 | 降到小模型，标记低置信度 | 超过 X 秒 |
| 限流（429） | 切备用模型 / 备用 Key | 连续 N 次 429 |
| 效果异常 | 熔断，走无 AI 的兜底逻辑 | 失败率超过 X% |
| 配额耗尽 | 提前告警 + 排队 | 余量低于 X% |

**「什么情况算异常」是产品判断，不是研发判断。** 所以这张表应该由产品来填。

## 空白模板

```markdown
## 1. 能力要求（硬门槛）
| 子能力 | 是否必须 | 判定方法 | 最低标准 |

## 2. 测试集分布对齐
| 维度 | 线上真实分布 | 测试集分布 | 对齐了吗 |

## 3. 候选模型对比
| 模型 | 能力达标吗 | 端到端耗时 | QPM/QPS | 单次业务成本 |
（能力不达标的直接标淘汰，不参与后面比较）

## 4. 并发核算
每分钟可服务用户数 = QPM ÷ 单次操作调用次数 = ______
对应能支撑的灰度比例 = ______

## 5. 成本三档
| 典型 / 较重 / 最坏 | 输入规模 | 单次成本 | 可接受吗 |
P99 超标时的产品硬限制：______

## 6. 分节点选型结论
| 节点 | 理解/生成类 | 错误可补救吗 | 调用次数看什么 | 选定模型 | 理由 |

## 7. 降级方案
| 故障场景 | 触发条件 | 降级策略 |
```

## 自检清单

- [ ] 能力要求拆成了可判定的子能力，不是「效果好」
- [ ] 做过「同一输入跑 5 次」区分缺失 vs 不稳定
- [ ] 测试集分布和线上分布逐维度对齐了
- [ ] 算的是端到端耗时，不是单节点
- [ ] 算过 QPM/QPS 折算出的业务并发上限
- [ ] 时延超标时先考虑了产品形态方案
- [ ] 所有模型参数都是显式设置的（不依赖默认值）
- [ ] 成本按「一次业务操作」算
- [ ] 算了三档，P99 超标时加了产品硬限制
- [ ] 知道哪个节点占成本大头，选型精力花在那里
- [ ] 成本包含了失败重试、辅助服务、存储
- [ ] 结论是分节点选型，不是全链路一个模型
- [ ] 每个关键节点有降级方案和明确触发条件

## 我还没搞清楚的

- 「视觉节点占 90%+ 成本」这条我只有一个项目的数据，不知道普适性如何。
- 大小模型协同的拆分粒度怎么定？我们是按「语义理解 vs 机械判断」拆的，但这个界线有时候很模糊。
- 降级到小模型之后，「标记低置信度」这个信息该不该告诉用户？我们当时没做，不知道做了会不会更好。
