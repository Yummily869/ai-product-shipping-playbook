# Agent 评测参考笔记

> ⚠️ **这篇是文献整理，不是我的实践总结。**
>
> 我做的是 AIGC 类产品，没有做过 Agent 类产品的评测。这份笔记是我为了理解「如果换到 Agent 场景，评测该怎么做」而整理的公开资料，来源包括 DeepEval / Confident AI、Galileo、Arize、NVIDIA 的公开文档。
>
> 之所以留在仓库里，是因为我发现 Agent 评测和 AIGC 评测的逻辑差异很大，这个对比本身让我对「评测到底在评什么」理解更清楚了。但里面所有内容我都**没有实际验证过**。

---

## 核心差异：评产出物 vs 评过程

AIGC 评测的是「产出物好不好」，Agent 评测的是「**过程对不对**」。

## 为什么不能沿用 AIGC 的评测方法

AIGC 产品是**单次输入 → 单次输出**，评测的是最终产出物的质量。

Agent 产品在给出答案之前，可能已经做了：制定计划、调用工具、检查工具返回、修正方案、维护状态、重试失败步骤、移交给子 Agent。**最终回复只是一条长执行路径的最后一个产物。**

这带来四个结构性困难：

| 困难 | 说明 |
|---|---|
| **错误会累积放大** | 一个早期的错误假设会污染后面每一步，最终看到的失败点通常离真正的错误点很远 |
| **执行路径长且自主** | 失败藏在轨迹深处，而不在最终回复里 |
| **轨迹是非确定的** | 同一输入每次走的路径可能不同，单次通过的测试几乎不说明问题 |
| **归因极难** | 检索器、工具、规划器、子 Agent 都在场，端到端分数只告诉你「坏了」，不告诉你「哪儿坏了」 |

**最关键的一条结论**：

> **Agent 可以每一步工具都调对，最终仍然没完成任务；也可以最终答对了，但路径极其低效昂贵。**
>
> 所以单一分数无法评测 Agent。

---

## 三层评测：一个诊断栈

行业已经收敛出的做法是**分三个深度评测**，按顺序使用：

```
① 端到端评测（End-to-End）
   把整个系统当黑盒 → 任务到底完成了没有？
        ↓ 如果没完成
② 轨迹评测（Trajectory）
   看计划、推理步骤、工具调用、重试、移交 → 路径是否合理高效？
        ↓ 如果路径有问题
③ 组件评测（Component）
   单独测某个检索器/工具/子 Agent → 究竟是哪个部件坏了？
```

**这个顺序不能颠倒**。先看结果，再看路径，最后定位部件。

> 端到端告诉你「**that** something broke」，组件级告诉你「**which** component broke」。

## 核心指标全表

| 指标 | 测什么 | 判定方式 | 适用层级 |
|---|---|---|---|
| **任务完成度**<br>Task Completion | 是否真的达成了用户目标 | LLM 判定 | 端到端 + 轨迹 |
| **工具选择正确率**<br>Tool Correctness | 是否调用了正确的工具 | **确定性** | 组件级 |
| **参数正确率**<br>Argument Correctness | 传给工具的参数对不对 | LLM 判定 | 组件级 |
| **步骤效率**<br>Step Efficiency | 有没有多余的步骤、重试、循环 | LLM 判定 | 轨迹级 |
| **计划质量**<br>Plan Quality | 行动前的计划是否完整、现实、高效 | LLM 判定 | 轨迹级 |
| **计划遵循度**<br>Plan Adherence | 执行中是否偏离了原计划与用户约束 | LLM 判定 | 轨迹级 |
| **推理相关性**<br>Reasoning Relevancy | 每一步推理是否服务于用户请求 | LLM 判定 | 组件级 |
| **推理连贯性**<br>Reasoning Coherence | 推理是否逻辑递进 | LLM 判定 | 组件级 |
| **检索类指标**<br>（忠实度/上下文精度/召回） | RAG 环节的检索与落地质量 | LLM 判定 | 组件级 + 端到端 |
| **安全性** | 输出是否有害、有偏见 | LLM 判定 | 端到端 + 组件级 |
| **时延 / 成本** | 生产环境的可持续性 | 确定性 | 全链路 |

### 一条重要原则：能确定性判定的，不要用 LLM 判定

> **确定性检查用于精确判定（工具名、必填参数、期望输出），LLM 判定用于需要主观判断的部分。**

这条原则能大幅降低评测成本，也提升可靠性。

**注意「工具选择正确率」是唯一一个纯确定性指标**——它不需要大模型参与，直接比对调用的工具集合与预期集合即可。

## 按 Agent 成熟度选指标

指标不是全都要用。**Agent 的自主程度决定了该评测什么**。

### L1 · 生成型 Agent

只响应提示（通常带检索上下文），不决定调什么工具、不编排多步流程。典型：基础客服问答、RAG 应用。

| 该测 | 该跳过 |
|---|---|
| 回答相关性、忠实度、上下文相关性/精度/召回、安全性 | 工具正确率、参数正确率、步骤效率、计划质量、计划遵循度 |

**原因**：没有真正的工具轨迹和计划可评。

### L2 · 工具调用型 Agent

可以决定何时调用 API、数据库、搜索、MCP 服务。**这是第一类「最终答案看起来对、但过程可能错」的 Agent**——它可能调错工具、传错参数，或走了一条昂贵的路。

| 该测 | 该跳过 |
|---|---|
| 工具正确率、参数正确率、步骤效率、任务完成度、回答相关性、安全性、时延、成本 | 计划质量、计划遵循度（除非它显式生成多步计划） |

### L3 · 规划型 Agent

构建多步工作流，根据结果调整执行选择。**可以每个工具调用单看都合理，但整体在执行一个糟糕的计划。**

| 该测 |
|---|
| L2 全部 + 计划质量、计划遵循度、推理相关性、推理连贯性 |

### L4 · 自主型 Agent

可主动发起行动、跨会话持续、根据反馈调整。

| 该测 | 该注意 |
|---|---|
| L3 全部 + 长周期任务完成度、生产监控、人工复核、子 Agent 组件级评测 | **不能只依赖单条测试用例**，必须有基于追踪的评测、生产采样、以及会随新失败模式增长的回归数据集 |

## 三个最容易被忽略的指标

### 1. 工具选择正确率不必是"完全匹配"

这是实践中最容易做错的地方。很多团队用严格的序列比对，导致大量假失败。

**两个应该放宽的维度**：

| 维度 | 说明 |
|---|---|
| **顺序无关性** | 只要必需的工具都用到了，调用顺序可能并不重要。此时应比对**集合**而非**序列** |
| **频次灵活性** | 某工具被调了几次，可能不如"是否选对了工具"重要 |

**举例**：一个医疗诊断 Agent 先查「病史数据库」再调「症状检查器」，还是反过来，只要两者都正确使用、信息都被纳入，诊断结论可能同样正确。

> **要不要放宽，取决于你的业务是否真的依赖顺序。** 这是一个必须由产品明确定义的判断，不能交给研发默认。

同样，参数正确率也不必要求完全匹配——**可以算"正确参数的百分比"**；如果输出是数值，**可以算与期望值的偏差百分比**。

### 2. 步骤效率：答对了也可能是失败

这是 Agent 评测独有的概念。

> **Agent 可以给出正确答案，但仍然应该判定为轨迹评测失败**——如果它调用了不必要的工具、传了错的参数、重复了同一步骤，或绕了一大圈才到。

一个直观例子：帮用户订机票的 Agent，先查天气、再换算汇率、最后才搜航班。它最终可能订到了票，但这条路径显然不合理。

**两个确定性的判定方法**：

| 方法 | 计算 |
|---|---|
| **冗余调用率** | 未直接贡献于结果的工具调用数 ÷ 总调用数 |
| **工具调用频次** | 对超过预设阈值（通常是 1 次）的工具调用做惩罚 |

**为什么必须测这个**：低效轨迹会同时推高**响应时延**和**运营成本**。一个又对又慢又贵的 Agent，在生产环境同样是失败的。

### 3. 计划质量 vs 计划遵循度：两个不同的问题

这两个极容易混为一谈，但它们指向不同的修复方向：

| 指标 | 问的问题 | 失败意味着 |
|---|---|---|
| **计划质量** | 行动**之前**的计划好不好 | 计划本身有问题 → 改规划 Prompt / 换更强的规划模型 |
| **计划遵循度** | 执行**过程中**有没有跑偏 | 计划是好的，但执行偏离 → 加约束 / 加中途校验 |

**「计划好但执行跑偏」在实践中非常常见**：Agent 一开始有个合理计划，然后跳过了验证步骤、重复了一个失败的工具调用、改动了请求范围之外的文件，或者因为某个工具返回了噪声输出就去追一个无关的错误。

> **只测最终结果，这两类问题会被混成同一个"失败"。**

## 追踪（Tracing）是整个体系的骨架

组件级评测必须建立在追踪之上。一条追踪记录了最终回复背后的每一个 span：检索调用、重排、工具调用、子 Agent 移交、生成器，以及每一步的**输入、输出、时延、成本**。

**追踪的两个价值**：

### 价值一：把低分回溯到具体 span

指标失败时，可以从最终输出沿着追踪走到出问题的那个 span，而不是猜哪个组件有责任。

> **一条追踪应该同时告诉你「分数是多少」和「问题出在哪」。**

### 价值二：发现你还没有指标的失败模式 🔥

这是更重要但更容易被忽略的价值。

> **你无法为一个还没见过的问题写指标。**

生产环境里 Agent 会以你从未预想的方式出错。可观测性能在你把问题形式化为指标**之前**，就暴露出信号。需要关注的异常信号：

| 信号 | 可能意味着 |
|---|---|
| 循环调用、同一工具重复调用远超平常 | 陷入死循环，即使还没有效率指标在监控 |
| 追踪深度、工具调用次数、时延、Token 成本在某类任务上突然飙升 | 原本便宜的任务变贵了 |
| 某些 span 报错、超时、返回空，然后被重试静默吞掉 | 失败被掩盖，统计上看不见 |
| 输出的语气、格式、结构相比上周发生漂移 | 模型版本或上游发生了变化 |

**处理流程**：

```
观察到异常信号
   ↓
打开追踪，判断是否为真实失败模式
   ↓
是 → 把它变成一个新指标 + 一条回归测试
```

> **追踪帮你发现"该评测什么"，而不只是执行你已有的评测。** 这是评测体系能持续进化的唯一机制。

## 人工复核：两个不可省的时刻

自动化指标仍然需要人在环中，尤其在早期。

| 时刻 | 做什么 | 为什么不能省 |
|---|---|---|
| **对齐指标与预期** | 信任一个指标之前，抽样真实追踪，检查它的通过/失败判定是否和你认为的好坏一致 | 这一步校准让 LLM 判定保持诚实，避免你在优化一个不反映真实标准的分数 |
| **捕捉漂移与行为变化** | 定期复核生产追踪样本 | 模型、Prompt、工具都在变，会出现当前指标设计时未考虑到的回归 |

**不需要复核全部**——目标是抽检到足够保持自动化评测可信，并把任何意外发现反哺回指标和数据集。

## 落地实践清单

按优先级排序，不要一次全上：

| # | 实践 | 说明 |
|---|---|---|
| 1 | **从小开始** | 先做任务完成度、工具正确率、回答相关性，不要一上来堆指标 |
| 2 | **评测路径，不只评测答案** | 轨迹（工具调用 + 推理）与最终输出同等重要 |
| 3 | **能确定性就确定性** | 工具名、必填参数、期望输出不需要 LLM 判定 |
| 4 | **主观部分用 LLM 判定** | 推理质量、任务完成度、有用性需要对上下文和意图做判断 |
| 5 | **下沉到组件级** | 分别评测检索器、工具、规划器、生成器，才知道**哪里**坏了 |
| 6 | **每个生产故障都变成回归测试** 🔥 | 数据集应该在每次 Agent 出丑时增长。**这也是为什么 Agent 能通过评测却在生产失败——如果数据集从不捕获真实故障** |
| 7 | **同时盯成本和时延** | 追踪工具调用次数和重试循环。又对又慢又贵，在生产环境仍是失败 |
| 8 | **每个指标都挂在追踪上** | 追踪是把低分连回到具体 span 的唯一方式 |

## 关于基准测试（Benchmark）的一个提醒

业界有 AgentBench、WebArena、SWE-bench 等标准基准，它们对**横向比较模型**有价值。

但：

> **基准测试不足以评测你的 Agent。** 它们无法代表你的生产工作流。你仍然需要自建数据集、基于追踪的评测，以及从真实故障构建的回归测试。

## 与 AIGC 评测的对照

| | AIGC 评测 | Agent 评测 |
|---|---|---|
| **评测对象** | 产出物质量 | 执行过程 + 最终结果 |
| **核心难题** | 主观效果难量化 | 归因难、轨迹非确定 |
| **拆分方式** | 按链路阶段拆维度权重 | 按评测深度分三层 |
| **主要判定方式** | 人工双评 + LLM 判定 | 确定性 + LLM 判定混合 |
| **数据集** | 基准测试集（只增不改） | 回归数据集（随故障增长） |
| **必须的基础设施** | 无（可人工执行） | **追踪系统（不可省）** |
| **典型失败** | 结果不好看 | 结果对但路径错 / 路径对但结果错 |

**一个共同点**：两者都必须输出**失败模式分布**而不只是分数，因为那张分布表才是迭代优先级。
