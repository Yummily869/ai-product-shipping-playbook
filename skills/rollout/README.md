# Skill · 灰度放量

> 用在什么时候：功能上线后决定要不要继续扩大流量的时候。

---

## 我一开始的理解是错的

我以为放量就是「先小流量看会不会崩，没问题就扩大」。

后来爆款复刻卡在 30% 的时候我才意识到：**这只解决了「会不会崩」，没解决「值不值得放」。**

放量至少要回答两个独立的问题：

| 问题 | 看什么指标 | 回答的是 |
|---|---|---|
| **技术稳定性** | 失败率、超时率、错误码分布 | 系统撑不撑得住 |
| **产品价值** | 转化率、完成率、留存 | 用户愿不愿意用 |

**这两个的答案可以各自独立地为「否」。** 我们遇到的情况就是技术指标完全正常，但转化率上不去——系统没问题，产品不够好。

**如果只盯技术指标，会一直放量，一直不知道哪里不对。**

---

## 两道门

我现在的理解是每个阶段要过两道门：

```
5% → 15% → 30% → 全量
  ↑       ↑       ↑
 两道门都过才能进下一阶段
```

### 技术门

| 指标 | 我们的阈值 |
|---|---|
| **视频生成失败率** | ≥ 50% 触发告警（爆款复刻实际配置） |
| P99 端到端耗时 | 超过约定上限 2 倍 |
| 限流错误占比 | > 5% |

### 价值门

| 指标 | 含义 |
|---|---|
| 完成率 | 发起生成 → 看到结果 |
| **导出率** | 看到结果 → 实际导出（爆款复刻的核心指标） |
| 次日留存 | 用过一次的用户次日还来吗 |
| 重新生成率 | 高 = 结果达不到预期 |

## 我们真实遇到的：爆款复刻卡在 30%

### 发生了什么

灰度到 30% 时发现**导出转化率偏低**，就暂停继续扩量了。

技术上没问题——失败率没到告警线，系统撑得住。但用户看到结果之后不导出。

**我现在觉得「卡在这里」这个决定是对的。** 继续放量只会让更多人看到一个「看了但不用」的功能，不会解决问题。

### 为什么盯导出率

因为爆款复刻的使用动机很明确：

> 用户来用这个功能，是因为**他们想发一条像爆款那样的视频**。
> 生成了但没导出，等于这次使用完全没产生价值。

导出率低我现在会按这个顺序排查：

```
Step 1：先看失败率
  失败率高 → 很多人根本没看到结果，是技术问题
  失败率正常 → 往下看

Step 2：看重新生成率
  高 → 结果看到了但不满意，在反复试
  低 → 看一眼就走，不是「不满意」是「不感兴趣」

Step 3：看在哪个环节退出
  看到结果页就退 → 结果质量问题（相似度不够）
  看了一会儿才退 → 操作路径或心理门槛问题
```

（这个排查顺序是我事后整理的，当时并没有这么系统。）

### 卡住的这段时间做了什么

**不放量不等于停工。** 这段时间我们并行做了两件事：

**① 调研 Minimax H3 模型**

爆款复刻的体验取决于视频生成模型的质量，原方案是 Seedance 2.0。调研 H3 是想评估：
- 相似度（对爆款视频的风格、运镜、节奏还原度）
- 成本
- 延迟和成功率

**这是预研，不是直接换。** 正确的做法是用同一批测试素材在两个模型上各跑一批，对比效果——而不是凭感觉换。

我从这件事想到一点：**放量卡住的时候其实是做模型预研的好时机**——有真实用户数据，有明确的待改进指标，又有时间做实验。全量放开之后反而更难换模型，因为那时候成本和风险都更大。

**② 制作爆款视频模板**

这是产品侧的另一条路：在纯生成方案之外补充模板路径。

两条路的差异：

| 路径 | 原理 | 适合什么 | 代价 |
|---|---|---|---|
| **纯生成**（Seedance / H3） | 模型理解爆款素材，生成新视频 | 素材质量好、风格可描述 | 成功率有波动、成本高 |
| **模板驱动** | 提取爆款的时间轴和转场结构，用户素材填进去 | 结构清晰的爆款 | 还原不了光效/运镜/情绪 |

**我当时的想法是这两条路不是二选一**，可以按素材质量和爆款类型分流：
- 素材质量好 + 运镜感强的爆款 → 走生成
- 素材一般 + 结构型爆款（开箱步骤、前后对比）→ 走模板

而且这个分流可以做成系统自动判断，用户不需要感知。

⚠️ **我实习结束时这两条路的对比还没有结论**，所以哪条更有效我不知道。

## 监控告警：为什么是 50%

爆款复刻的告警配置是：**视频生成失败率 ≥ 50% 时预警。**

我一开始觉得这个阈值太宽松了，10% 不是更保险吗？后来理解了为什么设 50%：

- 视频生成本身有一定基准失败率（Seedance 对上传素材有要求，用户传的素材不一定满足）
- 阈值设太低会频繁误告警
- 50% 是「一半用户拿不到结果」，这是明确的严重问题

**这让我学到一条我觉得挺重要的**：

> **告警阈值不是越低越严格越好。** 频繁误告警的后果是告警疲劳——团队开始忽略告警，真正的问题出现时反应反而更慢。
>
> 好的阈值应该是：**触发就一定需要人介入，不触发就可以放心。**

中间的灰色地带我觉得可以用「观察线」覆盖（比如 20%），触发时不发警报，只是不继续扩量。这个我们当时没做，是我后来想到的。

### 我觉得应该补的监控项

| 监控项 | 为什么 |
|---|---|
| 失败率**按错误码分类** | 「失败率 30%」没有行动价值，分清是素材问题还是模型服务问题才有 |
| P99 耗时（不只 P50） | P50 正常不代表长尾正常，视频生成的 P99 可能是 P50 的好几倍 |
| **导出率下降告警** | 上游服务静默降级（供应商升级模型小版本不通知）时，失败率可能不变，但导出率会先反映 |
| 按垂类的失败率 | 某个垂类失败率特别高时能定向优化 |

**「导出率下降告警」这一项我觉得最容易被漏掉**，因为它看起来像业务指标不像工程指标。但它其实是最灵敏的早期预警。

## 「继续放还是不放」

我事后整理出的判断矩阵：

| 技术稳定？ | 价值达标？ | 怎么做 |
|---|---|---|
| ✅ | ✅ | 继续扩量 |
| ✅ | ❌ | **暂停扩量，专注产品改进**（我们是这个情况） |
| ❌ | ✅ | 暂停扩量，专注稳定性 |
| ❌ | ❌ | 缩量或回滚，重新评估 |

**关键是「价值达标」的标准要提前定，不能卡住的时候才讨论。**

我建议在方案阶段就填这个：

```
进入下一阶段的前提条件（提前约定）：
  技术门：生成失败率 < ____%，P99 耗时 < ____ 秒
  价值门：导出转化率 > ____%，次日留存 > ____%
  观测窗口：至少 ____ 天（要够看趋势，不能看单日波动）
```

我们当时没有提前写这个，所以卡住的时候花了一些时间讨论「到底算不算达标」。**提前写下来能省掉这部分讨论。**

## 一个我后来想到但没做的拆分

**新用户和老用户应该分开看转化率。**

| 用户类型 | 他们的导出率代表什么 |
|---|---|
| 首次使用的新用户 | 产品能不能在第一眼打动人 |
| 主动找来的回访用户 | 产品能不能解决已知需求 |

我的理解是：
- **首次用户导出率低** → 问题可能在引导和预期管理（用户不知道这功能能干什么，或者期望和结果有落差）
- **回访用户导出率低** → 问题在功能本身（他们知道这能干什么，但产品做不到他们想要的程度）

**这两个问题的解法完全不同，用总体导出率是分不清的。** 这一点是我实习结束后回想才意识到的，当时只看了整体数字。

## 自检清单

**放量前**
- [ ] 技术门和价值门的具体指标和阈值写进文档了
- [ ] 观测窗口约定了（别看单日波动）
- [ ] 告警配好并测过（别等出问题才发现推送挂了）
- [ ] 降级方案定了（超阈值时自动降级还是人工暂停）

**放量中**
- [ ] 同时看技术指标和价值指标
- [ ] 按用户类型（首次/回访）分层看转化率
- [ ] 发现问题先拆分是技术问题（看错误码）还是产品问题（看转化路径）

**卡住的时候**
- [ ] 明确「解除卡点的前提条件是什么」，而不是靠感觉
- [ ] 把时间用在预研上（模型调研、替代方案），不是等待
- [ ] 模型预研有对照测试集（同一批素材两个模型都跑）

---

## 我还没搞清楚的

- 5% → 15% → 30% 这个节奏是怎么定的我其实不清楚，是团队既有的做法。为什么不是 10% → 30% → 50%？
- 观测窗口多久合适？我们没有明确约定，感觉是看情况。
- 卡在 30% 时，同时做模型调研和模板方案是不是分散了精力？如果只做一件事会不会更快出结论？这个我没有答案。
