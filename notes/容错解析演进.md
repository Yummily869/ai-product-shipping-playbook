# 容错解析代码是怎么一层层长出来的

> 一段代码从 1 行长到 30 行。每一层都是被一次线上问题逼出来的。
>
> 我觉得有价值的不是最终形态，而是**每一层是因为什么问题才加的**——因为你在新场景遇到的问题顺序会不一样。

---

## 背景

场景很典型：工作流节点调大模型做结构化信息提取，要求返回 JSON，下游节点消费这个 JSON。

Demo 阶段测了十几次，全部正常。

---

## V0 · 最开始

```python
def main(arg1) -> dict:
    return {"result": json.loads(arg1)}
```

**这个版本活了不到一天。**

---

## V1 · 加 try/except

**遇到的问题**：解析失败，整个工作流直接抛异常中断，用户端看到完全空白的结果。

**当时的想法**：至少别让整条链路崩掉。

```python
try:
    return {"result": json.loads(arg1), "isError": "0"}
except Exception as e:
    return {"result": {}, "isError": "1", "errorMsg": str(e)}
```

**代价**：把异常变成了错误码，但**还是不知道为什么失败**。日志里只有 `Expecting value: line 1 column 1`，这句话对定位问题完全没帮助。

---

## V2 · 区分 None 和空字符串

**遇到的问题**：出现了一批空指针类的错误。排查发现上游节点在某些条件下**根本没返回数据**——`arg1` 是 `None`。

这里我学到了一个我觉得很重要的判断：

> **`None`（上游没给数据）和 `""`（模型返回了空）是两个完全不同的问题，要找不同的人。**
>
> - `None` → 上游节点或链路配置问题 → 找研发
> - `""` → 模型没识别出内容 → 调 Prompt 或检查输入素材

如果这两个混在一个错误里，每次排查都要从头查一遍完整链路。**分开之后，看到错误码的瞬间就知道该往哪个方向查了。**

```python
if arg1 is None:
    return err("上游节点未返回数据")

raw = (arg1 if isinstance(arg1, str) else str(arg1)).strip()

if not raw:
    return err("未识别到有效内容")
```

**注意 `isinstance` 那一行。** 看起来多余，但工作流平台传下来的类型并不总是稳定的——有的平台会自动把 JSON 反序列化成 dict 再传，有的传原始字符串。不做类型防御，换个配置就会挂。

---

## V3 · 加正则抽取

**遇到的问题**：模型返回的内容长这样：

```
好的，我来帮你分析这个商品的信息：

{"category": "美妆", "audience": "25-35岁都市女性"}

以上就是分析结果，希望对你有帮助。
```

`json.loads` 面对这个必然失败。

**这个问题在 Demo 阶段完全没出现过**，因为 Demo 用的输入比较「标准」，模型也比较听话。真实输入下模型会时不时「多话」——尤其是输入本身有歧义的时候。

**解法**：不要求整个返回值是合法 JSON，只从里面抽出第一个 JSON 对象。

```python
m = re.search(r'\{[\s\S]*\}', cleaned)
if not m:
    return err("返回内容中未找到 JSON 结构")
obj = json.loads(m.group(0))
```

两个说明：
- 用 `[\s\S]` 而不是 `.`，因为 `.` 默认不匹配换行，而格式化的 JSON 一定有换行
- 这是**贪婪匹配**，抓「第一个 `{` 到最后一个 `}`」。如果返回里有多个独立 JSON 对象会抓错，那时要改成非贪婪或做括号配对

**代价**：这一层本质是在**容忍模型不遵守格式约束**。它降低了失败率，但也掩盖了「Prompt 的格式约束不够强」这个真实问题。

> **我觉得正确做法是两边都做**：Prompt 侧继续强化格式约束（降低发生率），解析侧做兜底（降低影响面）。只做解析侧兜底，等于放弃了改进上游的机会。

---

## V4 · 剥离思考过程

这是最隐蔽的一次，详细过程写在 [思考过程污染](./思考过程污染.md)。

一句话概括：**推理模型默认开启思考模式，平台 UI 把思考过程折叠了看不见，但传给下游的是原始文本。**

```python
cleaned = re.sub(r'<think>[\s\S]*?</think>', '',
                 raw, flags=re.IGNORECASE).strip()
```

---

## V5 · 分级错误码

**遇到的问题**：错误记录越来越多，但 `errorMsg` 是自由文本，没法聚合统计。答不出「这周的失败里，多少是上游问题、多少是模型问题」。

我定的错误码：

| 错误码 | 含义 | 找谁 |
|---|---|---|
| 15013 | 上游节点未返回数据 | 研发 |
| 15011 | 模型返回内容为空 | 产品（调 Prompt / 查素材） |
| 15012 | 内容无法解析为 JSON | 产品 + 研发 |

**我理解错误码的分类依据是「谁该去处理它」，而不是「技术上属于哪一类」。**

技术视角的分类（网络错误/解析错误/超时）对排查有用，但对推进解决没用。按责任方分类才能形成闭环。

### 分级之后多出来的一个好处

错误码能聚合之后，我自动得到了一份失败结构报表：

```
本周失败 1240 次
  15011 模型未识别内容    52%  ← 主要矛盾，调 Prompt / 加输入校验
  15012 格式解析失败      28%  ← 强化 Prompt 格式约束
  15013 链路异常           6%  ← 找研发排查
```

**这张表本身就是迭代优先级。** 而在只有一个笼统「失败」状态的时候，我只知道失败了 1240 次，不知道该先做什么。

## 最终形态

完整可运行版本（含 11 个测试用例）见 [toolkit/robust_json_parser.py](../toolkit/robust_json_parser.py)。

```python
def main(arg1) -> dict:
    # Layer 1: 上游数据存在性
    if arg1 is None:
        return _err("15013", "上游节点未返回数据")

    # Layer 2: 类型防御
    raw = (arg1 if isinstance(arg1, str) else str(arg1)).strip()

    # Layer 3: 剥离思考过程
    cleaned = re.sub(r'<think>[\s\S]*?</think>', '',
                     raw, flags=re.IGNORECASE).strip()

    # Layer 4: 空内容检查（必须在剥离之后）
    if not cleaned:
        return _err("15011", "模型未返回有效内容")

    # Layer 5: 抽取首个 JSON 对象
    m = re.search(r'\{[\s\S]*\}', cleaned)
    if not m:
        return _err("15012", "返回内容中未找到 JSON 结构")

    # Layer 6: 解析
    try:
        obj = json.loads(m.group(0))
    except Exception as e:
        return _err("15012", f"JSON 解析失败: {e}")

    # Layer 7: 类型确认
    if not isinstance(obj, dict):
        return _err("15012", f"解析结果类型异常: {type(obj).__name__}")

    return {"result": obj, "isError": "0", "errorMsg": "", "errorCode": ""}
```

## ⚠️ 一个让我排查很久的配置项

代码写对了，但**输出变量的类型声明如果没改，一切照旧失败**。

在工作流平台上，节点输出变量要显式声明类型。如果 `result` 声明的是 `string`，即使代码返回了 dict，平台也会把它序列化回字符串传给下游——**下游又得再解析一次，等于白做**。

| 变量 | 类型 |
|---|---|
| `result` | **object**（不是 string！） |
| `isError` | string |
| `errorMsg` | string |
| `errorCode` | string |

**这个坑的排查体验很差**：代码看着完全正确，日志打出来也正确，但下游就是拿不到对象。

我后来的经验是：**这种情况该问「数据在哪一层被改变了形态」，而不是「代码哪里写错了」。**

---

## 顺序为什么是这个顺序

有两处顺序是必须的：

### 1. 剥离思考过程必须在空值检查之前

```
❌ 判断 raw 是否为空 → 剥离 think 块
✅ 剥离 think 块 → 判断 cleaned 是否为空
```

因为存在一种情况：**模型只输出了思考过程，没输出实际内容**。此时 `raw` 非空（有 think 块），但 `cleaned` 为空。

按错误顺序，这个 case 会漏到后面，最终报成「解析失败」而不是「内容为空」——**归因方向就错了**。

### 2. 类型确认必须在 json.loads 之后

`json.loads` 成功不代表结果是 dict。`"[1,2,3]"` 和 `"123"` 都能成功解析，但类型不是下游期望的。

---

## 我从这件事总结的

### 1. 不要预防性地加容错层

上面 7 层不是设计出来的，是 **7 次问题逼出来的**。

我的感受是：**在没遇到问题时加的容错层，往往加错了地方**——因为猜的失败模式和真实的失败模式通常不一样。

**更好的做法是**：先留好观测（把原始输入输出打进日志），等问题出现再针对性加层。

### 2. 容错的目的是「保留归因能力」，不是「让流程不报错」

这是最容易做偏的地方。

一个 `try/except: pass` 的链路确实不会崩，但它**同时也失去了改进的可能**——你不知道失败了多少、为什么失败、该找谁。

**好的容错 = 不中断 + 可归因 + 可聚合统计。**

### 3. 提升成功率本身就是降本手段

模型调用一旦发出，即使结果不可用，Token 也已经消耗了。

一个 20% 解析失败率的链路，等于凭空多付 **20%** 的成本，而且这部分成本完全不产生用户价值。

**这一点是我后来算成本时才意识到的**：修好解析层可能比任何 Prompt 优化都更能降本，而且它不牺牲任何体验。
