# 监控告警配置清单

> 上线前应该配什么监控，以及「告警阈值怎么定」的判断方法。

---

## 先说一个常见的配置误区

很多团队的监控只有一层：**把所有指标都配上告警**，阈值拍脑袋设一个「感觉严格」的数字。

结果是**告警疲劳**：

> 告警每天触发十几次，团队开始默认「大概是正常波动」，告警提示音变成了背景噪音。
> 然后有一天真正的问题来了，比往常早了两小时，但没有人第一时间发现。

**告警的价值来自「触发了就一定需要人介入」**。如果告警可以安全忽略，这个告警就不该存在。

---

## 两层分级的设计思路

| 层级 | 触发逻辑 | 响应预期 |
|---|---|---|
| **P0 告警**（必须立刻响应） | 触发意味着用户受到显著影响，每分钟延误都在扩大损失 | 15 分钟内响应，需要立即判断是否降级或回滚 |
| **P1 观察线**（需关注但无需立刻响应） | 指标异常但未到用户大面积受损，有时间排查 | 1 小时内看一眼，判断是否上升为 P0 |

**这两层对应不同的阈值：**

- P0 阈值：「到这里就一定要有人看」，设偏宽松，确保触发就是真实问题
- P1 阈值：「可能有问题，提前关注」，设偏严格，作为早期预警

---

## 爆款复刻功能的监控配置

### 核心告警项

| 监控项 | P0 阈值 | P1 阈值 | 数据来源 |
|---|---|---|---|
| **视频生成失败率** | ≥ 50% | ≥ 20% | 错误码统计 |
| **P99 生成耗时** | > 约定上限 × 3 | > 约定上限 × 2 | 链路追踪 |
| **限流错误（15031）占比** | ≥ 10% | ≥ 5% | 错误码统计 |
| **导出转化率（小时维度）** | 低于 7 日均值 50% | 低于 7 日均值 30% | 埋点 |

**关于失败率的 50% 阈值**：这不是随意设的，而是一个明确的商业判断——一半用户拿不到结果，**等于该功能实际上已经半瘫痪**。50% 以下的失败率在有明确素材要求的视频生成场景中存在一定基准值（用户上传的素材不一定满足模型要求），不能把这部分当异常告警。

### 为什么需要「导出转化率下降」的告警

这一项容易被认为是业务指标而非工程指标，因此漏配。但它实际上是最灵敏的早期预警信号：

> **如果某个上游服务悄悄降级（模型版本切换、素材解析质量下滑），用户不会报错，但导出率会第一时间反映。**

很多上游变更是**静默发生**的（供应商升级了模型小版本，没有通知）。等到失败率上升，损失可能已经持续了好几天。

## 通用 AI 功能的监控配置模板

| 监控项 | 必须配 | 推荐配 | 原因 |
|---|---|---|---|
| **功能级失败率** | ✅ | — | 最核心的稳定性指标 |
| **失败率按错误码分类** | ✅ | — | 不分类的失败率无法定责 |
| **P99 端到端耗时** | ✅ | — | P50 正常不代表长尾正常 |
| **限流错误占比** | ✅ | — | 限流是最容易被忽视的故障类型 |
| **转化率（下游业务指标）** | — | ✅ | 技术指标正常但体验下降时的兜底 |
| **重新生成率** | — | ✅ | 高重试率 = 用户对结果不满意，比差评早 |
| **按垂类/画幅的分层失败率** | — | ✅ | 某类输入大面积失败时尽早发现 |
| **模型调用成功率（按供应商）** | — | ✅ | 供应商静默降级的早期信号 |

### 几个容易漏配的监控项

**① P99 vs P50 耗时，都要看**

- P50 正常：说明大多数用户体验正常
- P99 异常：说明一小部分用户（通常是输入较重的用户）等待时间极长

只看 P50 会掩盖长尾问题。尤其是视频生成这类「输入越长成本越高」的场景，P99 的耗时可能是 P50 的 5-10 倍。

**② 按错误码分类的失败率**

「失败率 30%」这个数字本身没有行动价值。分类之后才有：

| 错误码 | 含义 | 谁处理 |
|---|---|---|
| 素材不满足模型要求（用户侧） | 前置校验 + 文案改进 | 产品 |
| 模型服务超时（供应商侧） | 升配额、换模型 | 技术 |
| 链路内部报错 | 排查代码 | 研发 |

详见 [分级错误码设计](../03-robustness/error-code-design.md)。

**③ 功能入口的点击率**

这不是直接的质量指标，但它反映用户发现功能的效率。如果入口曝光率正常但点击率极低，说明用户看到入口但不知道这是干什么的——这是需求认知问题，不是质量问题。

## 告警阈值怎么定

这是最难回答的问题，通常有三种策略：

### 策略一：基于基准值 × 系数

```
告警阈值 = 历史 7 日均值 × (1 + 可接受波动系数)
```

适用条件：有足够的历史数据，且业务处于平稳阶段。

缺点：**新功能刚上线时没有历史数据**，用不了。

### 策略二：从用户体验反推

问自己：「失败率达到多少时，用户开始明显感知到这个功能不好用？」

然后把这个值作为 P0 阈值，前面一档作为 P1。

爆款复刻的 50% 就是这么定的：
- 失败率 50% → 两个用户里有一个拿不到结果 → 明确感知到功能不可用 → P0
- 失败率 20% → 五个里有一个失败 → 用户会遇到，但还在可接受范围 → P1 观察

### 策略三：用「告警触发但不需要人介入」的次数做校准

上线两周后，统计一下：
- P0 告警触发了几次？其中几次是真实需要人工介入的？
- 如果「误报」超过 30%，说明阈值设太严了，应该放宽

> **「误报率」是告警质量的核心指标**，但几乎从来不被主动追踪。

## 告警通知的配置原则

| 原则 | 说明 |
|---|---|
| **P0 必须有人接** | 不能只发到群里。至少要有一条路径确保 15 分钟内有人看到：电话/短信/专属提示音 |
| **P1 发群即可** | 工作时间看到即可，不需要打扰睡眠 |
| **告警内容要包含「下一步」** | 「失败率 52%」不是完整的告警。完整的应该是「失败率 52%（阈值 50%），当前在灰度 30%，请确认是否暂停扩量并查看错误码分布」 |
| **定期演练** | 每季度手动触发一次告警，确认通知链路完好。很多告警在真正需要时才发现推送挂了 |

## 一个真实的告警设计失误

某功能上线后配了「成功率 < 95% 时告警」。上线第一天触发了 7 次，全部是因为流量低峰期的正常波动（5 次请求 1 次失败就是 80%）。

团队把这 7 次全判断为噪音，然后把阈值调到「< 70%」。

两周后真实问题出现：成功率降到 68%，告警发出，但**团队已经养成了「告警 = 噪音」的习惯**，第一反应是「等等看」，耽误了 2 小时。

> **告警失去信任的过程是不可逆的**。一旦被标记为「通常没事」，它就会保持这个标签。
>
> 更好的做法是：**改善阈值的计算方法**（如用置信区间而非绝对值），而不是简单地把阈值调松。

对于低流量功能（早期灰度阶段），推荐用**时间窗口统计**代替实时值：

```
❌ 当前成功率 < 70%（5次里1次失败就触发）
✅ 过去30分钟失败次数 > N（绝对次数，不受流量影响）
```

## 上线前的监控自检清单

- [ ] 核心功能失败率已配告警，阈值有明确的推导依据（不是拍脑袋）
- [ ] 失败率告警是按错误码分类的，而不是一个总体值
- [ ] P99 耗时已配告警（不只有 P50）
- [ ] 限流错误（429 / 15031）单独告警
- [ ] P0 告警有明确的人工接单机制（不只是发群）
- [ ] 告警内容包含「当前状态 + 阈值 + 建议下一步动作」
- [ ] 配置完成后用测试数据触发过一次，确认推送链路完好
- [ ] 有评估告警质量的机制（定期统计误报率）
- [ ] 下游业务指标（转化率/导出率）有看板，即使不配告警
