# 灰度放量节奏设计

> 为什么放量不是「开关拨大」，以及卡在某个比例时该怎么判断要不要继续放。

---

## 先说一个真实的结构问题

很多团队把放量理解成「先小流量验证稳定性，没问题就扩大」。

**这只解决了「会不会崩」，没解决「值不值得放」。**

AI 产品的放量至少要回答两个相互独立的问题：

| 问题 | 对应指标 | 可能的答案 |
|---|---|---|
| **技术稳定性** | 失败率、超时率、错误码分布 | 能不能放：系统撑不撑得住 |
| **产品价值** | 转化率、完成率、使用深度 | 值不值得放：用户愿不愿意用 |

**这两个问题的答案可以互相独立地为「否」。**

一个很常见的情况是：技术稳定性完全达标（失败率 3%，一切正常），但转化率始终上不去——系统没问题，但产品不够好。**如果只盯技术指标，你会一直放，一直不知道哪里不对。**

---

## 放量卡点：每个阶段该看什么

一个可以直接套用的放量框架。**每进入下一阶段之前，两道门都要过。**

```
5% → 15% → 30% → 全量
  ↑       ↑       ↑
 技术门  技术门  价值门（更严）
```

### 技术门：系统能不能撑

| 指标 | 建议阈值 | 超过则暂停扩量 |
|---|---|---|
| **视频生成失败率** | < 50%（告警线）/ < 20%（正常线） | ✋ 暂停 |
| P99 端到端耗时 | 不超过约定上限 2 倍 | ✋ 暂停 |
| 错误码 15031（限流）占比 | < 5% | ✋ 暂停，先扩容 |
| 服务端异常率 | < 1% | ✋ 暂停 |

**第一行「50%」是实测采用的告警阈值**：到了这个位置意味着一半用户拿不到结果，**必须暂停放量并启动排查**。

20% 是日常的健康线目标。两条线同时存在是有意义的：告警线触发的是「立刻停」，健康线触发的是「不继续放，但当前流量可以维持」。

### 价值门：用户值不值得看

| 指标 | 含义 | 低于预期怎么处理 |
|---|---|---|
| **完成率** | 发起生成 → 看到结果 | 先查失败率（技术问题）vs 放弃率（产品问题） |
| **导出率** | 看到结果 → 实际导出 | ⚠️ 这是核心价值门，见下方 |
| **次日留存** | 用过一次的用户，次日还来用吗 | 评估是否解决真实需求 |
| **重新生成率** | 用户看到结果后重新生成的比例 | 高 = 结果达不到预期 |

## 案例：爆款复刻卡在 30% 的六周

### 发生了什么

「爆款复刻」功能（基于 Seedance 2.0 视频生成）在灰度到 30% 后发现**导出转化率偏低**，随即暂停继续扩量。

这是一个标准的「技术稳定但产品价值不达预期」的卡点。

**「卡在这里」本身是一个正确的决策**。继续放量只会放大一个「用户看了但不用」的问题，而不会解决它。

### 为什么是导出率，而不是用完即走

导出率是爆款复刻功能最核心的价值指标，原因在于这个功能的使用动机：

> 用户用爆款复刻，是因为**他们想发出一条像爆款那样的视频**。
> 如果生成了一条视频但最终没有导出，等于这次使用完全没有产生价值。

导出率低的可能原因（按定位顺序排查）：

```
Step 1：先看失败率
  失败率 > 20% → 大量用户根本没看到结果，技术问题优先
  失败率正常   → 继续往下看

Step 2：看重新生成率
  高重新生成率 → 结果看到了，但不满意，在反复尝试
  低重新生成率 → 用户看了一眼就走，不是「不满意」是「不感兴趣」

Step 3：看用户在哪个环节退出
  看到结果页就退 → 结果质量问题（相似度不够、生成效果差）
  看了结果才退   → 操作路径或心理门槛问题
```

### 这段时间做了什么

**不放量不等于停工。** 卡在 30% 的这段时间是产品侧和技术侧并行调研的窗口：

**① 调研 Minimax H3 模型**

爆款复刻的核心体验取决于视频生成模型的质量。原有方案是 Seedance 2.0，调研 Minimax H3 是为了评估：
- 相似度（对爆款视频的风格、运镜、节奏的还原度）
- 成本
- 延迟与成功率

**这是模型升级的预研，不是放弃原方案**。正确的做法是用同一批测试素材在两个模型上各生成一批，对比相似度和导出意愿——而不是直接换。

这也说明一条通用规律：

> **放量卡点是做模型预研的最佳时机**——有真实用户行为数据，有明确的待改进指标，又有时间做实验。**全量放开之后反而是最难换模型的时候**，因为那时成本和风险都更大。

**② 制作爆款视频模板**

这是产品侧的并行探索：在纯生成方案之外，补充模板化的路径。

两种路径的本质差异：

| 路径 | 原理 | 适用场景 | 代价 |
|---|---|---|---|
| **纯生成**（Seedance 2.0 / H3） | 模型理解爆款素材，生成新视频 | 素材质量好、风格可描述 | 成功率有波动、成本高 |
| **模板驱动** | 提取爆款的时间轴和转场结构，用户素材填入 | 结构清晰的爆款 | 无法还原光效/运镜/情绪 |

> **两条路不是非此即彼**，而是可以根据输入素材质量和爆款类型做分流：
> - 素材质量好 + 运镜感强的爆款 → 走生成路径
> - 素材质量一般 + 结构型爆款（如「开箱步骤」「前后对比」）→ 走模板路径

**这个决策本身就可以成为一个产品功能点**：系统自动判断走哪条路，不需要用户感知。

## 监控配置：失败率的两条线

爆款复刻功能的监控设计：

| 线 | 阈值 | 触发动作 |
|---|---|---|
| **告警线** | 视频生成失败率 ≥ 50% | 立即通知，评估是否暂停放量 |
| **健康线（建议补充）** | 失败率 ≥ 20% | 人工关注，不继续扩量 |

**为什么设在 50%，而不是 10%**

这个选择背后有一个判断：

- 视频生成（Seedance 2.0）本身有一定基准失败率（因为对素材有要求）
- 把阈值设太低（如 10%），会频繁触发误告警，导致告警被忽视
- 50% 是「一半用户都没法拿到结果」，这是明确的严重问题

**这也是一个经常被低估的告警设计原则**：

> **告警阈值不是越低越严格越好。** 频繁触发误告警的后果是「告警疲劳」——团队开始忽略告警，真正的问题出现时反应时间反而更长。
>
> **好的阈值设计是：触发意味着一定需要人工介入，不触发意味着可以放心。** 两个区域中间的灰色地带用「建议关注线」覆盖，不触发警报。

### 告警之外：应该补充的监控项

| 监控项 | 类型 | 说明 |
|---|---|---|
| 失败率（按错误码分类） | 告警 | 分清是素材问题还是模型服务问题（见错误码设计） |
| P99 生成耗时 | 告警 | 超时不一定产生失败，但影响体验 |
| 导出率（按用户分层） | 看板 | 区分「新用户首次体验」vs「回访用户」，两种转化率意义不同 |
| 重新生成次数分布 | 看板 | P99 重试 3 次以上的用户，是深度体验还是反复踩坑 |
| 按垂类的失败率 | 看板 | 某个垂类（如户外、宠物）失败率显著更高时，定向优化 |

## 「再放还是不放」的决策框架

卡在某个灰度比例时，面临的选择不是非此即彼的两条路，而是这个矩阵：

| 技术稳定？ | 价值达标？ | 决策 |
|---|---|---|
| ✅ | ✅ | **继续扩量** |
| ✅ | ❌ | **暂停扩量，专注产品改进**（爆款复刻就是这个情况） |
| ❌ | ✅ | **暂停扩量，专注稳定性** |
| ❌ | ❌ | **大幅缩量或回滚，重新评估** |

**「价值达标」的判断标准必须提前定义，不能在卡住的时候才讨论。**

推荐做法：在设计方案时就填这张表：

```
进入下一阶段的前提条件（提前约定，不在评审会上争）：
  技术门：视频生成失败率 < ____%，P99 耗时 < ____ 秒
  价值门：导出转化率 > ____%, 次日留存 > ____%
  观测窗口：至少观测 ____ 天（足够看稳定趋势，而非单日波动）
```

> **把「达标」的标准写进方案文档，是避免放量决策变成意见战的唯一方法。**

## 一条容易被忽略的放量节奏建议

**新用户和老用户的分流测试**

刚开始放量时，往往只看整体指标。但有一个有价值的拆分：

| 用户类型 | 特征 | 指标含义不同 |
|---|---|---|
| **首次使用的新用户** | 不知道这个功能能做什么，预期是空白的 | 他们的导出率代表「产品能不能在第一眼打动人」 |
| **主动找来的回访用户** | 知道功能存在，有具体诉求 | 他们的导出率代表「产品能不能解决已知需求」 |

> **如果首次用户导出率低，问题通常在「引导与预期管理」**——用户不知道这个功能能做什么，或者期望和实际结果有落差。
>
> **如果回访用户导出率低，问题通常在「功能本身」**——他们知道这能干什么，但产品做不到他们想要的程度。

这两个问题的解法完全不同，用总体导出率是分不清的。

## 检查清单

**放量前**
- [ ] 技术门和价值门的具体指标和阈值已写入文档
- [ ] 观测窗口已约定（避免单日波动误判）
- [ ] 告警配置已上线并测试（不要等到问题出现才知道告警不生效）
- [ ] 降级方案已定义（失败率超阈值时自动降级还是人工暂停）

**放量中**
- [ ] 同时看技术指标和价值指标，不只看技术指标
- [ ] 按用户类型（首次/回访）分层看转化率
- [ ] 每次发现问题，先拆分是技术问题（错误码）还是产品问题（转化路径）
- [ ] 放量卡住时，把时间用在预研而非等待（模型调研、模板制作、指标分析）

**卡点期间**
- [ ] 明确「解除卡点的前提条件是什么」，而不是靠感觉判断
- [ ] 模型预研有对照测试集（同一批素材，两个模型都跑一遍）
- [ ] 模板方案和生成方案的分流依据是否已定义
- [ ] 告警疲劳评估：过去 X 天告警触发了几次？有几次是真实问题？
