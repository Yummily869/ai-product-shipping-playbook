# 线上问题图谱

> 按「**暴露时机**」分类，而不是按技术类型分类。

---

## 为什么按暴露时机分类

大多数问题清单是按技术类型分的（模型问题 / 工程问题 / 数据问题）。这种分法在**排查时**有用，但在**预防时**没用——因为你不知道该在哪个阶段去找它。

按暴露时机分类能直接回答一个更有用的问题：

> **我现在处在哪个阶段，接下来最可能爆的是什么？**

## 分层图谱

```
┌─────────────────────────────────────────────────────┐
│ L1 · Demo / 试运行阶段就能发现                        │
│    输出格式不稳定、Prompt 不遵循、明显幻觉             │
├─────────────────────────────────────────────────────┤
│ L2 · 只有换环境才会暴露  ← 最容易漏                   │
│    平台层封装差异、参数默认值差异、上下游拼接差异       │
├─────────────────────────────────────────────────────┤
│ L3 · 只有真实输入分布才会暴露  ← 最难归因              │
│    画幅/时长/格式边界、空值与极端值、垂类分布偏移       │
├─────────────────────────────────────────────────────┤
│ L4 · 只有规模化才会暴露                               │
│    配额限流、并发瓶颈、长尾超时、成本超预算            │
├─────────────────────────────────────────────────────┤
│ L5 · 只有长期运行才会暴露                             │
│    模型版本漂移、效果衰减、用户行为迁移                │
└─────────────────────────────────────────────────────┘
```

**关键判断：Demo 阶段能发现的问题（L1）只是全部问题的一小部分。** 而 L2 和 L3 是最容易在项目排期里被忽略的两层——因为它们不在任何人的责任范围内：算法觉得模型没问题，研发觉得代码没问题，产品觉得设计没问题，但组合起来就是不行。

## L1 · Demo 阶段可发现

| 问题 | 典型现象 | 定位难度 |
|---|---|---|
| 输出格式不稳定 | 要求 JSON，有时返回带解释文字的 JSON | ★ |
| 指令遵循度不足 | 明确要求「不超过 50 字」，实际经常超 | ★ |
| 输出粒度过粗 | 要求提取用户标签，返回「女性」这类无信息量结果 | ★★ |
| 明显幻觉 | 编造不存在的商品参数 | ★ |

这一层的共同特点：**改 Prompt 就能解决**，且改完立刻能验证。

> 关于「输出粒度过粗」的详细解法（黑名单机制 + 维度强制组合 + Few-shot 对错示例），见 [Prompt 约束设计](../02-pipeline/prompt-constraints.md)。

## L2 · 换环境才暴露 🔥

**这一层最危险，因为它会造成「我这边是好的」这种最难推进的争论。**

| 问题 | 典型现象 |
|---|---|
| **平台 UI 掩盖了真实输出** | 工作流试运行看起来正常，测试环境下游节点拿到脏数据 |
| **参数默认值差异** | 平台不显式设置某参数时，走的是模型默认值，而默认值可能与预期相反 |
| **上下游拼接假设不一致** | 上游以为传的是对象，下游按字符串处理 |
| **环境间模型版本不一致** | 测试环境和生产环境指向了不同的模型版本 |

### 代表案例：推理模型的思考过程污染下游

**现象**：工作流里单独试运行某节点，输出干净漂亮。但集成到完整链路后，下游节点收到的内容里混着大段思考过程，导致解析失败。

**为什么试运行看不出来**：平台 UI 把思考过程折叠成了一个「已深度思考(x秒)」的标签，视觉上完全看不见。但**传给下游节点的是未经处理的原始文本**。

**根因**：使用的是推理模型，而推理模型**默认开启思考模式**。产品侧从来没有主动开启过这个功能，所以完全没想到它是开着的。

**这里有一个极易踩的坑**：平台的参数配置面板通常有两个开关——
- 左边：**是否覆盖该参数**
- 右边：**参数值**

「左关右关」的含义不是「关闭思考模式」，而是「**不覆盖，走模型默认值**」——而默认值是开启。要真正关闭，必须是「**左开（启用覆盖）+ 右关（值为关闭）**」。

**解法（双保险）**：

```
第一层（参数）：显式覆盖参数，关闭思考模式
第二层（解析）：下游解析时正则剥离 <think>...</think>
```

只做第一层不够，因为参数配置可能被误改、可能在其他环境不生效；只做第二层不够，因为思考过程本身消耗大量 Token 和时间。

**实测收益**：单次调用耗时约 **72 秒 → 2.5 秒**，Token 消耗约 **4500 → 750**。

**代价**：关闭思考模式会损失模型在复杂推理任务上的质量。所以正确做法不是全局关闭，而是**按节点区分**——需要复杂推理的节点保留，只做结构化输出的节点关闭。

### 如何提前发现 L2 类问题

**唯一有效的方法：不要相信平台 UI 展示的结果，去看下游节点实际收到的原始内容。**

具体做法：在链路的每个节点后临时插入一个「透传打印」节点，把上游传下来的**原始字符串**完整打出来。这一步在联调阶段花 20 分钟，能省下后面两周。

## L3 · 真实输入分布才暴露 🔥

| 问题 | 典型现象 |
|---|---|
| **画幅/格式边界** | 横屏正常、竖屏大面积失败（见下） |
| **上游素材规格约束不透明** | 模型侧对输入有严格要求，不满足直接失败，但错误信息无法转译给用户 |
| **极端值未覆盖** | 纯黑画面、无人声、超短素材（<3s）、超长素材 |
| **垂类分布偏移** | 通用策略在某个垂类完全失效 |
| **上下文语义冲突** | 自动生成的标签里带了风格词，与用户显式选择的风格互相矛盾 |
| **上游结果被错误复用** | 用户没有输入意图时，误用了上一节点的推荐结果，导致主题漂移 |

### 代表案例一：横竖屏导致的 badcase 率 0% vs 70%

完整案例见 [输入分布陷阱](./input-distribution-trap.md)。一句话概括：

> 上游方测 50 个视频 0 例问题，我方 badcase 率 70%。根因是双方默认的画幅不同——横屏字幕消除良好，竖屏失效。**双方都没意识到自己有「默认画幅」这个前提。**

### 代表案例二：语义空间重叠导致的上下文冲突

**现象**：用户明确选了「诗意表达」风格，生成的文案却是吐槽风。

**根因**：链路上游会自动为素材打「内容标签」，而部分内容标签本身**携带了风格语义**。这些带风格的内容标签和用户显式选择的风格标签一起被拼进 Prompt，两者互相矛盾，模型只能二选一。

**解法**：把内容标签和风格标签的**语义空间彻底解耦**——内容标签只描述「拍了什么」，严禁出现任何描述「怎么讲」的词。

**这是一条通用认知**：

> **多个来源的信息拼进同一个 Prompt 时，必须保证它们的语义空间不重叠。** 重叠即冲突，冲突时模型的选择是不可预测的。

### 如何提前发现 L3 类问题

建一张**输入分布对照表**，在测试集设计阶段就填：

| 维度 | 线上真实分布 | 测试集分布 | 是否对齐 |
|---|---|---|---|
| 画幅比例 | 竖屏 90% | | |
| 时长分布 | P50=25s, P99=300s | | |
| 是否含原生字幕 | 60% | | |
| 垂类分布 | 美食 30% / 亲子 20% / ... | | |
| 极端输入占比 | 空/黑/无声 约 3% | | |

**任何一行「不对齐」，都是一个潜在的线上事故。**

## L4 · 规模化才暴露

| 问题 | 典型现象 | 预防手段 |
|---|---|---|
| **配额耗尽 / 限流** | 突然大面积失败，返回 429 `insufficient_quota` | 提前压测，配置余量告警 |
| **QPS / QPM 达顶** | 高峰期排队，等待时间飙升 | 明确并发上限，设计排队与降级 |
| **长尾任务超时** | P50 正常但 P99 超时严重 | 按输入分档，长输入走不同策略 |
| **成本超预算** | 平均成本可控，长尾成本失控 | 按 P99 输入算成本，加硬上限 |

### 关于配额问题的一个提醒

`429 insufficient_quota` 这类错误**不是代码问题**，但它会以「产品大面积不可用」的形式呈现。这类问题的关键不是修复，而是：

1. **能否快速识别**——错误码必须能区分「模型能力问题」和「配额/限流问题」，否则会浪费大量时间排查代码
2. **能否自动降级**——配额打满时，是直接报错，还是切换备用模型/备用 Key？
3. **能否提前预警**——余量告警必须在打满之前触发

> 这也是为什么需要 [分级错误码](./error-code-design.md)：「失败」这一个状态无法支撑上述任何一条。

### 并发能力必须在方案阶段就算清楚

以一个真实链路为例：模型侧 QPM 120、QPS 2。

**QPM 120 意味着什么？** 如果一次业务操作需要调用该模型 4 次，那么理论上一分钟只能服务 30 个用户。这个数字必须在放量决策前算出来，否则灰度到某个比例就会撞墙。

推导公式：

```
每分钟可服务用户数 = QPM ÷ 单次业务操作的调用次数
安全放量比例 ≈ 每分钟可服务用户数 ÷ 高峰期每分钟请求用户数
```

## L5 · 长期运行才暴露

| 问题 | 说明 |
|---|---|
| **模型版本漂移** | 供应商静默升级模型，同样的 Prompt 效果变化 |
| **效果衰减** | Prompt 与真实用户表达方式逐渐脱节 |
| **用户行为迁移** | 上线初期的用户和放量后的用户是两类人，策略需要重新验证 |
| **成本结构变化** | 模型降价或涨价，单位经济模型需要重算 |

这一层的应对不是技术手段，而是**机制**：固定周期的效果回归 + 一个稳定不变的基准测试集。

## 一张自查清单

上线前逐项确认，每一项都对应上面某个真实事故：

**L2 环境类**
- [ ] 是否直接查看过下游节点收到的**原始字符串**（而非平台 UI 展示的结果）？
- [ ] 所有模型参数是否**显式设置**（而非依赖默认值）？特别是思考模式、温度、max_tokens
- [ ] 测试环境与生产环境的模型版本是否一致？

**L3 分布类**
- [ ] 测试集的画幅/时长/格式分布是否与线上一致？
- [ ] 是否测过极端输入：空值、超长、超短、纯黑、无声？
- [ ] 拼进同一个 Prompt 的多来源信息，语义空间是否有重叠？
- [ ] 上游节点的结果在什么条件下**不应该**被下游复用？

**L4 规模类**
- [ ] 模型侧的 QPM / QPS 上限是多少？折算成业务并发是多少？
- [ ] 按 P99 输入算，单次成本是多少？是否加了硬上限？
- [ ] 配额告警是否配置？阈值是多少？
- [ ] 失败时的降级路径是什么？

**通用**
- [ ] 错误码是否能区分「模型问题 / 输入问题 / 配额问题 / 上游无数据」？
- [ ] 每一类错误对用户展示的文案是否不同？
