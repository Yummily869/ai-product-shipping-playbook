# 输入分布陷阱

> 当上游方说「我们复现不了你的问题」时，你该做什么。

---

## 这是本手册最想传达的一条认知

> **AI 产品绝大多数「诡异」的线上问题，根因不是模型能力不足，而是输入分布不一致。**

「输入分布不一致」有三种形态：

| 形态 | 表现 |
|---|---|
| **Demo 分布 ≠ 线上分布** | 你演示时用的是精挑的素材，用户传的是随手拍的 |
| **你的分布 ≠ 上游的分布** | 模型供应商测的是通用素材，你的场景有隐含约束 |
| **测试集分布 ≠ 真实分布** | 评测集里 badcase 率 5%，线上 40% |

第二种最危险，因为它会**让你误判归因方向**——你会以为是自己的用法有问题，而实际上是双方在测完全不同的东西。

---

## 案例：一个消耗了大量沟通成本的横竖屏问题

### 问题

在一个「参考视频生成同类视频」的功能中，提测时 badcase 率高达 **70%**。核心问题是：原视频的字幕消除不掉，导致生成结果出现**双字幕**（原视频自带字幕 + 我们叠加的新字幕同时出现在画面上）。

70% 是一个不可能上线的数字。

### 第一轮归因（错误方向）

第一反应是怀疑自己的 Prompt 写得不对——因为模型供应商的官方文档里有专门的提示词撰写指南，而我们可能没有严格遵循。

于是走了这条路径：

1. 找模型供应商团队协助排查
2. 对方提供了一份提示词撰写方法
3. 按照方法调整后，**问题依旧**

到这一步，投入产出比已经开始变差了——因为方向可能从一开始就是错的。

### 关键转折：对方复现不了

对方团队用他们的方式测试了 **50 个视频，0 例出现双字幕**。

这是整个排查过程中最重要的信息，但当时它带来的第一反应是困惑而不是启发：

> 同一个模型、相似的提示词，为什么我们 70% 出问题，他们 0% 出问题？

**这里有一个很容易走进去的死胡同**：继续对比提示词的细微差异、参数配置、调用方式。这些都是「我们做错了什么」的思路，而正确的问题是——

> **我们和他们，输入的到底是不是同一类东西？**

### 真实根因

经过长时间沟通比对，最终定位到：

> **横屏视频的字幕消除效果良好，竖屏视频出现双字幕的概率极高。**

而这个差异之所以隐蔽，是因为它是**双方各自的默认前提，从来没有被显式说出来过**：

- 模型供应商团队测试时，默认用**横屏**素材（通用视频生成场景的主流形态）
- 我们的产品是**移动端竖屏为主**的场景，测试素材几乎全是竖屏

**双方都以为在讨论同一件事，实际上测的是两个不同的输入分布。**

### 解法

根因定位后，解法路径就清晰了。但注意——**根因定位并不等于问题能被根治**：

竖屏字幕消除是模型侧的能力短板，不是我们能改的。所以最终采用的是**在链路中前置一个字幕擦除 API**，先把原视频字幕擦掉，再送进生成模型。

### 代价

| 代价 | 说明 |
|---|---|
| **增加成本** | 多一次外部 API 调用，单次生成成本上升 |
| **增加链路长度** | 多一个节点 = 多一个失败点，端到端成功率承压 |
| **增加耗时** | 擦除是同步前置步骤，直接加在用户等待时间上 |
| **只是降低而非消除** | 擦除 API 本身也有效果边界，复杂字幕仍可能残留 |

这是一个典型的「**用工程手段绕过模型能力短板**」的决策。它不优雅，但它能上线。

## 从这个案例抽象出的方法

### 1. 「对方复现不了」是信号，不是噪音

当上游方（模型供应商 / 平台方 / 另一个团队）说复现不了你的问题时，**这个信息的价值极高**，因为它把问题范围从「模型有 bug」缩小到了「两边输入不一致」。

正确的下一步不是继续调参数，而是**逐项比对双方的输入特征**。

### 2. 输入特征比对清单

跨团队定位效果问题时，先把这张表填完再讨论。视频/图像类场景可以直接用：

| 维度 | 我方 | 对方 |
|---|---|---|
| **画幅比例** | 竖屏 9:16 | ? |
| **分辨率范围** | | |
| **时长分布** | | |
| **是否含原生字幕/水印** | | |
| **码率 / 编码格式** | | |
| **是否含人声 / BGM** | | |
| **内容垂类分布** | | |
| **来源**（用户上传 / 素材库 / 专业拍摄） | | |

> 这张表里的任何一行不一致，都足以造成 0% vs 70% 的 badcase 率差异。

对话类 / 文本类场景把维度换成：query 长度分布、是否含错别字与口语化表达、是否含多意图混杂、语种混杂比例、上游 ASR 是否引入噪声。

### 3. 「默认前提」必须被显式写出来

这个案例的根本教训不是「要注意横竖屏」，而是：

> **每一方都有一堆自己觉得理所当然、根本不会主动提的默认前提。这些前提是跨团队沟通中最大的信息黑洞。**

实践做法：在向外部团队报效果问题时，附上一份**输入样本的特征说明**（而不只是「我们效果不好，请帮忙看看」）。一句「我们的素材是竖屏、用户手机拍摄、平均 30 秒、多数自带字幕」，可能省下两周的沟通。

## 案例二：素材约束不透明导致的高失败率

### 问题

同一个功能，生成视频失败率很高。

### 根因

模型侧对用户上传的视频素材有**较严格的格式与规格要求**（时长、编码、分辨率等），不满足时直接失败。而这些要求：

- 在文档中不够显眼
- 用户完全不可能知道
- 失败时返回的错误信息无法转译成用户能理解的话

### 解法

在链路中前置**素材解析与校验**，并设计**明确的异常 toast** —— 失败时告诉用户「你的素材哪里不符合要求」，而不是笼统地说「生成失败，请重试」。

### 代价与产品决策

这里有一个真实的产品取舍：

| 选项 | 优点 | 缺点 |
|---|---|---|
| 前置校验 + 明确报错 | 用户知道怎么改，减少无效重试 | 转化漏斗多一道卡点，部分用户会直接流失 |
| 不校验，让它失败后重试 | 链路短 | 用户不知道为什么失败，反复重试推高成本，体验极差 |
| 前置校验 + **自动转码修复** | 体验最好 | 增加成本与耗时，且不是所有问题都能自动修复 |

最终选了第一种。判断依据是：**在能力有明确边界的场景下，「让用户知道边界」比「假装没有边界」的长期体验更好。**
