# 容错解析的演进

> 一段代码从 1 行长到 30 行的全过程。每一层都是被一次线上问题逼出来的。

---

## 为什么这一章重要

大多数关于 AI 工程的文章会直接给你一段"最佳实践"代码。但**最终形态本身没有教学价值**——有价值的是「**每一层是因为什么问题才加的**」。

因为你在新场景下遇到的问题序列会不一样，你需要的不是抄一段代码，而是理解**判断该加哪一层的逻辑**。

---

## 背景

场景很典型：一个工作流节点调用大模型做结构化信息提取，要求模型返回 JSON，下游节点消费这个 JSON 的字段。

Demo 阶段测了十几次，全部正常。

---

## V0 · 天真版本

```python
def main(arg1) -> dict:
    return {"result": json.loads(arg1)}
```

**这个版本存活了不到一天。**

---

## V1 · 加 try/except

**触发问题**：解析失败，整个工作流直接抛异常中断，用户端看到的是完全空白的结果。

**当时的想法**：至少不要让整条链路崩掉。

```python
def main(arg1) -> dict:
    try:
        return {"result": json.loads(arg1), "isError": "0"}
    except Exception as e:
        return {"result": {}, "isError": "1", "errorMsg": str(e)}
```

**代价**：把异常变成了错误码，但**依然不知道为什么失败**。日志里只有 `Expecting value: line 1 column 1`，这句话对定位问题毫无帮助。

---

## V2 · 加空值检查

**触发问题**：出现了大量 `errorMsg` 为空指针类错误的记录。排查发现上游节点在某些条件下**根本没有返回数据**——`arg1` 是 `None`。

这里有一个关键认知：

> **`None`（上游没给数据）和 `""`（模型返回了空）是两个完全不同的问题，需要分别定位到不同的人。**
>
> - `None` → 上游节点/链路配置问题 → 找研发
> - `""` → 模型没识别出内容 → 调 Prompt 或检查输入素材

如果这两者混在一个错误里，每次排查都要从头查一遍。

```python
def main(arg1) -> dict:
    # 上游完全没给数据
    if arg1 is None:
        return {"result": {}, "isError": "1",
                "errorMsg": "上游节点未返回数据"}

    raw = (arg1 if isinstance(arg1, str) else str(arg1)).strip()

    # 模型返回了但内容为空
    if not raw:
        return {"result": {}, "isError": "1",
                "errorMsg": "未识别到有效内容"}

    try:
        return {"result": json.loads(raw), "isError": "0"}
    except Exception as e:
        return {"result": {}, "isError": "1", "errorMsg": str(e)}
```

**注意 `isinstance` 那一行。** 它看起来多余，但工作流平台传下来的类型并不总是稳定的——某些平台会自动把 JSON 结构反序列化成 dict 再传给下一个节点，某些情况下传的是原始字符串。**不做类型防御，换个平台或改个配置就会挂。**

---

## V3 · 加正则抽取

**触发问题**：模型返回的内容大致长这样：

```
好的，我来帮你分析这个商品的信息：

{"category": "美妆", "audience": "25-35岁都市女性"}

以上就是分析结果，希望对你有帮助。
```

`json.loads` 面对这段内容必然失败。而这个问题**在 Demo 阶段完全没出现过**，因为 Demo 时用的输入比较"标准"，模型的输出也比较听话。

真实输入分布下，模型会时不时"多话"——尤其是输入本身有歧义时。

**解法**：不要求整个返回值是合法 JSON，只从中**抽取出第一个 JSON 对象**。

```python
    m = re.search(r'\{[\s\S]*\}', cleaned)
    if not m:
        return {"result": {}, "isError": "1",
                "errorMsg": "返回内容中未找到 JSON 结构"}
    obj = json.loads(m.group(0))
```

**关于这个正则的两个说明**：

- 用 `[\s\S]` 而不是 `.`，是因为 `.` 默认不匹配换行，而格式化的 JSON 一定有换行
- 这是**贪婪匹配**，抓的是「第一个 `{` 到最后一个 `}`」。如果返回里有多个独立 JSON 对象，会抓错。此时应改用非贪婪 `\{[\s\S]*?\}` 或做括号配对计数

**代价**：这一层本质是在**容忍模型不遵守格式约束**。它降低了失败率，但也掩盖了"Prompt 的格式约束不够强"这个真实问题。

> **正确做法是两边都做**：Prompt 侧继续强化格式约束（降低发生率），解析侧做兜底（降低影响面）。只做解析侧兜底，等于放弃了改进上游的机会。

---

## V4 · 剥离推理过程

**触发问题**：这是最隐蔽的一次。

工作流里单独试运行该节点，输出看起来完全正常。但集成到完整链路后，下游拿到的内容里混着大段思考过程，解析失败率飙升。

**为什么试运行看不出来**：平台 UI 把思考过程折叠成了一个「已深度思考(x秒)」的小标签，**视觉上完全看不见**。但传给下游节点的是**未经任何处理的原始文本**。

**根因**：用的是推理模型，而推理模型**默认开启思考模式**。产品侧从来没有主动开启过，所以完全没有怀疑过这一点。

**解法是双层的**：

**第一层（参数侧）**：显式关闭思考模式。

这里有一个平台层面的坑：参数配置面板往往有**两个开关**——

| 开关 | 含义 |
|---|---|
| 左侧 | 是否**覆盖**该参数 |
| 右侧 | 参数**值** |

「左关右关」的实际含义**不是**「关闭思考模式」，而是「**不覆盖，走模型默认值**」，而默认值是开启。真正关闭需要「**左开 + 右关**」。

> 这类"看起来关了其实没关"的配置，是 AI 产品里非常高频的一类误判。**只要参数与预期行为不符，第一件事是确认参数是否真的生效了。**

**第二层（解析侧）**：正则剥离思考块。

```python
    cleaned = re.sub(r'<think>[\s\S]*?</think>', '',
                     raw, flags=re.IGNORECASE).strip()
```

**为什么两层都要做**：

| 只做参数层 | 只做解析层 |
|---|---|
| 参数可能被误改 | 思考过程会消耗大量 Token 和时间 |
| 其他环境可能不生效 | 成本和耗时问题不解决 |
| 换模型后默认值可能又变了 | |

**实测收益**（关闭思考模式后）：单次调用耗时约 **72 秒 → 2.5 秒**，Token 消耗约 **4500 → 750**。

**代价**：关闭思考模式会损失模型在复杂推理任务上的质量。

> **所以不能全局关闭，要按节点区分**：
> - 需要复杂判断的节点（如剪辑思路规划）→ 保留思考
> - 只做格式化输出的节点（如信息提取、分类打标）→ 关闭思考

## V5 · 分级错误码

**触发问题**：错误记录越来越多，但 `errorMsg` 是自由文本，无法聚合统计。没法回答「这周的失败里，多少是上游问题、多少是模型问题」。

详见 [分级错误码设计](./error-code-design.md)。这里只放最终代码。

---

## 最终形态

```python
import re
import json


def main(arg1) -> dict:
    """
    从上游节点的模型输出中稳健地提取 JSON 对象。

    错误码约定：
      15013 - 上游节点未返回数据（链路/配置问题 → 研发）
      15011 - 模型返回内容为空（Prompt/输入问题 → 产品）
      15012 - 内容无法解析为 JSON（格式约束问题 → 产品/研发）
    """
    # ---- Layer 1: 上游数据存在性 ----
    if arg1 is None:
        return _err({}, "15013", "上游节点未返回数据")

    # ---- Layer 2: 类型防御 ----
    # 平台可能传 str，也可能传已反序列化的对象
    raw = (arg1 if isinstance(arg1, str) else str(arg1)).strip()

    # ---- Layer 3: 剥离推理模型的思考过程 ----
    cleaned = re.sub(r'<think>[\s\S]*?</think>', '',
                     raw, flags=re.IGNORECASE).strip()

    # ---- Layer 4: 空内容检查（在清洗之后判断）----
    if not cleaned:
        return _err({}, "15011", "模型未返回有效内容")

    # ---- Layer 5: 抽取首个 JSON 对象 ----
    m = re.search(r'\{[\s\S]*\}', cleaned)
    if not m:
        return _err({}, "15012", "返回内容中未找到 JSON 结构")

    # ---- Layer 6: 解析 ----
    try:
        obj = json.loads(m.group(0))
    except Exception as e:
        return _err({}, "15012", f"JSON 解析失败: {e}")

    # ---- Layer 7: 类型确认 ----
    # 正则可能抓到 JSON 数组或标量，下游期望的是对象
    if not isinstance(obj, dict):
        return _err({}, "15012", f"解析结果类型异常: {type(obj).__name__}")

    return {
        "result": obj,
        "isError": "0",
        "errorMsg": "",
        "errorCode": "",
    }


def _err(default, code, msg):
    return {
        "result": default,
        "isError": "1",
        "errorMsg": msg,
        "errorCode": code,
    }
```

---

## ⚠️ 一个极易被忽略的配置项

代码写对了，但**输出变量的类型声明如果没改，一切照旧失败**。

在工作流平台上，节点的输出变量需要**显式声明类型**。如果 `result` 原本声明为 `string`，即使代码返回了 dict，平台也会把它序列化回字符串传给下游——**下游又得再解析一次**，等于白做。

| 变量 | 类型 |
|---|---|
| `result` | **object**（不是 string！） |
| `isError` | string |
| `errorMsg` | string |
| `errorCode` | string |

> 这个坑的排查体验极差：代码看着完全正确，日志打出来也正确，但下游就是拿不到对象。**排查方向应该是"数据在哪一层被改变了形态"，而不是"代码哪里写错了"。**

---

## 顺序为什么是这个顺序

各层的顺序不是随意的，有两处是**必须**的：

**1. 剥离思考过程必须在空值检查之前**

```
错误顺序：判断 raw 是否为空 → 剥离 think 块
正确顺序：剥离 think 块 → 判断 cleaned 是否为空
```

因为存在一种情况：模型**只输出了思考过程，没输出实际内容**。此时 `raw` 非空（有 think 块），但 `cleaned` 为空。按错误顺序，这个 case 会漏到后面，最终报成"解析失败"而不是"内容为空"——**归因方向就错了**。

**2. 类型确认必须在 json.loads 之后**

`json.loads` 成功不代表结果是 dict。`"[1,2,3]"` 和 `"123"` 都能成功解析，但类型不是下游期望的。

## 抽象出的通用方法

### 1. 每一层容错都对应一个真实故障，不要预防性地加层

上面 7 层不是设计出来的，是**7 次线上问题逼出来的**。

反过来说：**在没有遇到问题时加的容错层，往往加错了地方**。因为你猜的失败模式和真实的失败模式通常不一样。

**正确的姿势**：留好观测（把原始输入输出打进日志），等问题出现，然后针对性加层。

### 2. 容错的目的是「保留归因能力」，不是「让流程不报错」

这是最容易做偏的地方。

一个只会 `try/except: pass` 的链路确实不会崩，但它**同时也失去了改进的可能**——你不知道失败了多少、为什么失败、该找谁。

**好的容错 = 不中断 + 可归因 + 可聚合统计。**

### 3. Prompt 侧和解析侧都要做，缺一不可

| 侧面 | 作用 |
|---|---|
| **Prompt 侧**（格式约束、Few-shot、明确禁止解释性文字） | 降低问题**发生率** |
| **解析侧**（本章内容） | 降低问题**影响面** |

只做 Prompt 侧 → 总有漏网的，且模型版本一变就复发
只做解析侧 → 掩盖了上游问题，且解析层会越来越复杂

### 4. 提升成功率本身就是最直接的降本手段

模型调用一旦发出，即使结果不可用，Token 也已经消耗。

一个 20% 解析失败率的链路，等于凭空多付 **20%** 的成本，而且这部分成本**完全不产生用户价值**。

> 这是鲁棒性与成本的连接点。在很多项目里，**修好解析层比任何 Prompt 优化都更能降本**。详见 [多模态节点是成本大头](../04-cost/multimodal-dominance.md)。
