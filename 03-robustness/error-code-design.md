# 分级错误码设计

> 为什么「失败」这一个状态不够用。

---

## 问题

大多数 AI 产品链路的初版错误处理长这样：

```python
try:
    result = call_model(prompt)
except Exception as e:
    return {"isError": "1", "errorMsg": str(e)}
```

它能防止链路崩溃，但会导致三件事做不了：

| 做不了什么 | 具体表现 |
|---|---|
| **无法定责** | 失败了，该找研发、找算法、还是产品自己调 Prompt？ |
| **无法聚合统计** | `errorMsg` 是自由文本，无法回答「这周失败里各类占比多少」 |
| **无法差异化提示用户** | 所有失败都只能显示「生成失败，请重试」 |

第三点的代价最大：**当失败原因是"用户的素材不符合要求"时，让他重试是纯粹的浪费**——他重试一百次也是同样的结果，而每次重试你都在付 Token 成本。

---

## 核心原则

> **错误码的分类依据是「谁该去处理它」，而不是「技术上属于哪一类」。**

这是最容易做偏的地方。技术视角的分类（网络错误 / 解析错误 / 超时）对排查有用，但对**推进解决**没用。

按责任方分类才能形成闭环：

| 错误码 | 含义 | 责任方 | 处理动作 |
|---|---|---|---|
| **15013** | 上游节点未返回数据 | 研发 | 查链路配置、查上游节点是否执行 |
| **15011** | 模型返回内容为空 | 产品 | 调 Prompt，或检查输入素材质量 |
| **15012** | 内容无法解析为目标格式 | 产品 + 研发 | Prompt 侧强化格式约束 + 解析侧加容错 |
| **15021** | 输入不满足能力边界 | 产品 | 前置校验 + 明确告知用户 |
| **15031** | 配额耗尽 / 限流 | 运维 | 扩容、切备用 Key、配降级 |
| **15041** | 超时 | 研发 | 调阈值、加降级路径 |

---

## 为什么 15011 和 15013 必须分开

这是最有价值的一次拆分。两者在代码里的表现极其相似（都是"没拿到有效内容"），但**根因和处理方式完全不同**：

```python
# 15013：上游根本没给数据
if arg1 is None:
    ...

# 15011：上游给了，但模型输出是空的
if not cleaned:
    ...
```

| | 15013 | 15011 |
|---|---|---|
| **发生位置** | 链路层 | 模型层 |
| **典型原因** | 分支条件没走通、变量映射错误、上游节点异常退出 | 输入素材质量差、Prompt 有歧义、模型拒答 |
| **找谁** | 研发 | 产品 |
| **能否自愈** | 否，是 bug | 可能，换素材或调 Prompt |
| **给用户看什么** | 「系统异常，请稍后再试」 | 「未能识别出内容，请更换素材」 |

**如果这两者混成一个错误码**，每次排查都要从头走一遍完整链路，而 80% 的情况其实只需要看其中一侧。

> 实际体感：拆开之后，定位方向在**看到错误码的瞬间**就确定了，而不需要先去捞日志判断问题出在哪一层。

## 编码规范建议

```
1 5 0 1 2
│ │ └─┴─┴── 具体错误（01=空数据, 02=格式错误, ...）
│ └──────── 责任域（1=数据/内容, 2=输入校验, 3=资源, 4=性能）
└────────── 业务模块标识
```

**三条约定**：

1. **同一责任域的错误码连续** —— 便于用前缀做聚合统计（例如统计所有 `150 1x` 就得到全部内容类问题）
2. **错误码只增不改** —— 一旦上线就是数据口径的一部分，改了会导致历史数据无法对比
3. **每个错误码必须有对应的用户文案** —— 没有用户文案的错误码等于没设计完

---

## 与用户提示的映射

错误码是给内部看的，用户看到的必须是另一套语言。

| 错误码 | 内部含义 | 用户看到的 | 是否引导重试 |
|---|---|---|---|
| 15013 | 上游未返回数据 | 系统繁忙，请稍后再试 | ✅ 是 |
| 15011 | 模型未识别到内容 | 未能识别素材内容，建议更换素材 | ❌ 否 |
| 15012 | 格式解析失败 | 生成异常，请重试 | ✅ 是 |
| 15021 | 输入超出能力边界 | 你的素材时长超过 X 分钟，请裁剪后重试 | ⚠️ 修改后重试 |
| 15031 | 配额耗尽 | 当前使用人数较多，请稍后再试 | ✅ 是（但需延迟） |
| 15041 | 超时 | 生成时间较长，已为你转为后台处理 | — |

**「是否引导重试」这一列是产品决策，不是技术决策。**

判断依据：**重试是否有可能成功？**

- 15011（素材本身没内容）→ 重试必然还是失败 → **不应引导重试**，应引导换素材
- 15013（链路瞬时异常）→ 重试可能成功 → 引导重试
- 15031（限流）→ 立即重试会加剧限流 → 引导重试但要加延迟

> **一个反面案例**：把所有失败都做成「点击重试」按钮。用户在素材不合规的情况下连点五次，五次都失败，而每一次你都付了完整的模型成本。**这不只是体验问题，是真金白银的浪费。**

## 落地检查清单

- [ ] 每个错误码都能明确指向一个责任方
- [ ] 「上游无数据」和「模型输出为空」是两个独立错误码
- [ ] 「能力边界不满足」有独立错误码，且**前置校验**而非事后报错
- [ ] 配额/限流类错误与模型能力类错误分开（否则会浪费大量时间排查代码）
- [ ] 每个错误码有对应的用户文案
- [ ] 每个错误码明确了「是否引导重试」
- [ ] 错误码已落表，可用于聚合统计
- [ ] 关键错误码配置了告警阈值

---

## 一个额外收益：错误码是评测体系的入口

当错误码可以聚合统计后，你会自动获得一份**按周的失败结构报表**：

```
本周失败 1,240 次
  15011 模型未识别内容    52%  ← 主要矛盾，需要调 Prompt / 加输入校验
  15012 格式解析失败      28%  ← 需要强化 Prompt 格式约束
  15031 配额限流          14%  ← 需要扩容
  15013 链路异常           6%  ← 需要研发排查
```

**这张表本身就是迭代优先级排序。** 而在只有一个笼统"失败"状态的系统里，这张表根本不存在——你只知道失败了 1240 次，不知道该先做什么。
